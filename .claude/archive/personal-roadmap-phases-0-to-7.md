# Avito-project: roadmap до готового продукта

## Context

Старый план «dapper-hugging-wozniak» (удалён в фазе 0a) был структурно
плоский: резал работу горизонтально (миграции → один сценарий → другой
сценарий → ...), из-за чего мы по 5 раз возвращались в одни и те же
файлы, а владелец как продакт-овнер не видел готовых кусков продукта
пока не закрывался весь критический путь. Этот план — замена старого,
нарезанная **вертикально по поверхностям, которые видит конечный
пользователь**.

База бизнес-модели зафиксирована в [`docs/BUSINESS_LOGIC.md`](../../docs/BUSINESS_LOGIC.md)
(660 строк, канон). Код после рефакторинга 2026-04-29 покрывает её на ~80%
(13 миграций Phase A-H применены, tsc 0, тексты DM везде placeholder).
Этот план описывает путь от текущего состояния до готового к продаже
B2B-SaaS продукта.

**Конечный результат:** одна полностью отлаженная инсталляция с настоящими
ботами, рабочей панелью, AI-продажником на Авито, объединёнными
аналитиками и шаблоном для быстрого развёртывания следующих клиентов.

## Онбординг нового чата (как сессия входит в контекст)

Любая новая сессия должна за минуту получить полную картину «что за
проект, в какой фазе, как работаем, куда копать дальше». Для этого:

1. **`CLAUDE.md`** (читается автоматически Claude'ом при старте) —
   компактный файл-навигатор. Что за продукт, бизнес-модель в одном
   абзаце, текущая фаза, команды, роли, метод работы (walkthrough),
   ссылки на канон и план. Без подробностей — подробности в указанных
   файлах.
2. **`.claude/handoff.md`** (тоже читается каждой сессией) — что было
   в последних сессиях, что сейчас на руках, что следующий шаг,
   неочевидные решения за период.
3. **`MEMORY.md` + memory-файлы** (`~/.claude/projects/.../memory/`) —
   подсказки про пользователя, бизнес-модель, технические правила.
   Читается Claude'ом автоматически.
4. **`docs/BUSINESS_LOGIC.md`** — канон бизнес-модели (660 строк).
   Читается когда нужно понять как должно работать.
5. **`.claude/plans/avito-project-b2b-drifting-haven.md`** (этот файл) —
   roadmap до готового продукта. Читается когда сессия начинает новую
   фазу или подтему.
6. **`.claude/walkthrough-notes.md`** — живой буфер с правками/идеями
   по walkthrough'у. Читается во время фазы 1-2.

Любые подробности (DATABASE, NAVIGATION, DESIGN_SYSTEM, AI_SALES,
AVITO_BRIEF) — отдельные файлы в `docs/`, упомянутые в CLAUDE.md
с одной строкой описания «когда читать».

## Принципы работы

### 1. Walkthrough-режим как основной метод

В начале каждой темы (бот, экран, секция панели) я делаю три шага в чате:

1. **Показываю текущее состояние** — реальный экран бота / страницы из
   реального запущенного dev-окружения, не из чтения кода.
2. **Спрашиваю про неочевидные сценарии** — что ты видишь в финальной
   версии чего нет в коде / каноне / памяти, какие есть пробелы.
3. **Шаг за шагом**: каждый текст, каждая кнопка, каждое уведомление,
   каждая ветка — обсуждаются и фиксируются. Не пропускаем ничего «потом
   доделаем» — это тот самый «потом» который никогда не наступает.

После одобрения — правка кода + спеки в `BUSINESS_LOGIC.md` + handoff.

### 2. Реверс-трассировка к панели

Пока ходим по ботам, у каждого сценария где требуется действие владельца
в web-панели — пишу строку в `.claude/walkthrough-notes.md` в раздел
«Требования к панели». К моменту перехода к Owner Panel у нас уже готовая
спека панели, ничего не выдумываем заново.

То же для требований к схеме БД, AI-продажнику, Авито-интеграции,
shipper-PWA — каждое всплывающее требование уходит в свой раздел.

### 3. Walkthrough-notes как живой буфер

Файл [`.claude/walkthrough-notes.md`](../walkthrough-notes.md) с разделами
по фазам и подтемам. Я пишу туда в реальном времени всё что не вписывается
в текущий шаг (идеи, баги, уточнения, требования к будущим фазам). В конце
каждого дня — прохожу по нему и применяю / переношу в spec / закрываю.

### 4. Smoke перед углублением

Перед детальным walkthrough'ом каждой большой темы я гоняю реальный код
на dev и сверяю с каноном. Если найдено сильное расхождение — фиксирую
ДО разговора с тобой, чтоб мы не путали «как должно» с «как сейчас».

### 5. Definition of Done у каждой фазы

Не «вроде всё», а конкретный чек-лист:

- Все walkthrough-сценарии пройдены и одобрены.
- Тексты согласованы (без placeholder).
- TypeScript 0 ошибок, lint 0.
- Документация обновлена (DATABASE.md, NAVIGATION.md, BUSINESS_LOGIC.md,
  handoff.md, MEMORY.md).
- Тесты на критических путях зелёные.

Только после галочки — переходим к следующей фазе.

### 6. Канон — единый источник правды

Если по итогам walkthrough'а что-то меняется в бизнес-модели — правится
[`docs/BUSINESS_LOGIC.md`](../../docs/BUSINESS_LOGIC.md), потом код, потом
тесты. Не код-первым.

### Фаза 1 — Telegram-структура (~1.5–2 недели)

**Цель:** все 4 бота и 2 группы доведены до production-качества.
Каждый текст согласован, каждая кнопка работает, каждое уведомление
звучит так как ты хочешь.

**Метод:** walkthrough из принципа 1, тема за темой.

**Подтемы (порядок):**

1. **Customer-bot** (~3 рабочих дня)
   - Bootstrap (`/start`), приветствие, авто-создание `customers`
   - Главное меню (5 reply-кнопок) — формулировки, иконки
   - Профиль (имя, телефон, дефолтная служба, +ВАЙБ-блок, баланс-блок)
   - Каталог (без категорий, поиск по тексту, карточка товара)
   - **Wizard оформления заказа** (6 шагов: товар → размер → служба →
     трек → `send_by` → реквизиты+чек/+ВАЙБ) — каждый шаг отдельно
   - Vision auto-confirm чеков: правила, ошибки, лимит 5 попыток,
     эскалация
   - +ВАЙБ-флоу: «Оплатить позже», заморозка/разморозка, wizard
     погашения долга (FIFO своих + per-партнёр), >50k → ручное
     подтверждение владельца
   - **«Мои заказы»** × 6 фильтров × кнопки на карточке × 9 статусов
   - **Wizard возврата**: трек → код → `pickup_by`, переоткрытие из
     `trash`, отмена возврата
   - Баланс: «Запросить вывод» → status «Запрошено N₽»
   - **DM-уведомления** по жизненному циклу заказа (создан, в сборке,
     printed, sent, return, return_done, trash, cancelled, problem) —
     все формулировки
   - **Trumpet-серия** (sequences по расписанию из memory
     `trumpet_notify_design.md`: 0/30/60/120 мин и далее каждые 3ч до
     21:00 МСК — «мини-история» с разной формулировкой на каждом шаге,
     не спам)
   - **«Плохое качество»**-флоу: ≥3 фото, причина, инструкция в
     Авито-поддержку, без возврата на склад
   - Edge cases: отмена wizard'а, лимит Vision, блокировка бота
     клиентом, падение сети

2. **Owner-bot** (~1 рабочий день)
   - DM-only, секретный username
   - Главное меню (или его отсутствие — обсудить)
   - DM-алерты: новый клиент, новый заказ, низкий остаток,
     +ВАЙБ-заморозка, daily-shipper-cleanup auto-revert,
     `problem`-каскад
   - DM-кнопки: подтвердить +ВАЙБ ≥50k, списать вывод баланса,
     подтвердить погашение партнёра
   - Что ещё нужно владельцу из бота (быстрый список, статус заказа,
     действия) — обсудить, может быть существенно

3. **Partner-bot** (~1 рабочий день)
   - Bootstrap по invite-link
   - «Активные заказы» (список, реквизиты клиента, треки)
   - DM-флоу нового заказа: ✅ получил оплату / ❌ не получил →
     реквизиты для клиента → трек
   - Возврат партнёрского: 4 кнопки результата, без trumpet
   - «Долг по комиссиям»: список заказов формирующих долг, wizard
     погашения владельцу с Vision-чеком
   - «Списать с баланса @ник» (после возврата клиенту)
   - **Phase F+ TODO:** групповая оплата клиентом нескольких заказов
     одному партнёру — нужен ли, как UI

4. **Shipper-bot** (~0.5 рабочих дня)
   - Главное меню (минимальное — все действия в PWA)
   - DM-алерты: новый заказ в общем пуле, возврат пришёл,
     auto-revert «не довёл до printed/sent» (с тегом для KPI)
   - Сценарий «никто из отправщиков не онлайн» — обсудить

5. **Клиентская группа** (~0.5 рабочих дня)
   - Постинг основных событий (создан, в сборке, отправлен)
   - Что НЕ постится (возвраты — личное дело клиента)
   - Топики или плоско, формат карточки

6. **ЧЕКИ-группа** (~0.5 рабочих дня)
   - Пост чека на каждый заказ
   - Caption формат («самодостаточный» — reply на заказ из другой

## End-to-end верификация (после фазы 7)

1. Развёртывание тестового клиента через bootstrap за ≤2 часа.
2. Импорт демо-каталога и клиентов через CSV без ошибок.
3. Обычный клиент: заказ → оплата → сборка → отправка → закрыт.
4. +ВАЙБ-клиент: несколько заказов в долг → группировка → погашение
   одним чеком; заморозка и разморозка автомат + ручная.
5. Партнёрский заказ: клиент платит партнёру → партнёр отправляет →
   возврат → партнёр возвращает деньги → долг по комиссиям погашается.
6. Расхождение склада: отправщик жмёт «нет товара» → каскад → возврат

   человека.
8. Выплата отправщику: подтверждение перевода, запись в ledger.
9. Все тесты (unit + e2e + RLS) зелёные, билд чистый.
10. Визуальный проход: ощущение качества (фаза 5).
11. PITR работает, восстановление из бэкапа проверено.
