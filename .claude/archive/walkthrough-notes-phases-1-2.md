## 🚫 Отложено по решению владельца (фаза 2)

> Сценарии которые ТЕОРЕТИЧЕСКИ полезны, но владелец сознательно решил
> не добавлять: они редки или покрываются другими механизмами. Чтобы
> не возвращаться к ним в будущих сессиях.

- **«Вернуть N₽ клиенту» в карточке заказа `/owner/orders/[id]`**
  (отложено 2026-05-14). Частичный возврат денег по конкретному заказу
  с привязкой `order_id` к записи в `customer_balance_history`. В UI
  такого action'а нет. **Почему отложено:** редкая ситуация (бракованный
  товар оставлен у клиента + частичная компенсация / двойная оплата).
  Покрывается универсальной кнопкой ➕ Пополнить на карточке клиента
  (`/owner/clients/[id]`) — комментарий в записи (например «по заказу
  №X, брак») остаётся в `customer_balance_history.note`. Минус —
  привязка к заказу только текстом, не структурно. Если ситуации
  начнут учащаться — добавить отдельную кнопку с RPC.
- **«Отметить проблему» владельцем в `/owner/orders/[id]`**
  (отложено 2026-05-14). Возможность владельца вручную поставить
  заказ в `status='problem'` с причиной. В UI такого action'а нет.
  **Почему отложено:** очень редкий сценарий — проблему обычно ставит
  отправщик из shipper-PWA через `executeMarkProblem`
  (out_of_stock / bad_barcode). Если владельцу нужно — он использует
  Cancel order. Manual mark владельцем = признак того, что shipper-flow
  что-то пропустил.
- **Отдельная страница `/owner/returns`** (отложено 2026-05-14).
  План фазы 2 предполагал отдельный раздел «Возвраты» с общим списком +
  фильтрами + действиями. **Почему отложено:** доступ есть через
  `/owner/orders` с фильтром по `status in (return / return_done / trash)`.
  Отдельная страница = дублирование списочного UI ради одного фильтра.
  Если в фазах 4-5 (аналитика / редизайн) появится «дашборд возвратов»
  со специфичной аналитикой — добавим тогда. Для оперативной работы
  фильтра достаточно.

### Каталог (экран 3) — inline-режим

**Архитектура:** категорий нет совсем. Reply-кнопка `📋 Каталог` шлёт
промежуточное сообщение «Выбор товара тут 👇» с inline-кнопкой
`🔍 Начать поиск` (тип `switch_inline_query_current_chat`). Тап
открывает у клиента поле ввода `@<bot> ` — ввод стримится в бота как
`inline_query`, ответ — список карточек с превью-фото.

**В @BotFather** для customer-bot включён Inline Mode, placeholder —
`Что ищем?`.

**Сортировка топа** (пустой query): `is_premium DESC, created_at DESC`.

**Поиск** (с query): `ILIKE` по `name` и `brand` (description пока не
ищем — слишком шумно).

**Карточка-превью в inline-панели:**

```
🛍 {название}
{Премиум | }Дроп: X ₽ | Авито: Y ₽
Размеры: S, M, L | Город: Москва
```

Превью-фото слева — `mainPhotoUrl(product)`. Если фото нет — карточка
без миниатюры (article).

**После клика по карточке:**

1. Telegram отправляет в чат от имени клиента короткое сообщение
   «🛍 {название товара}» (через `input_message_content`) — оно остаётся
   в нативной истории как «факт выбора».
2. `chosen_inline_result` → бот шлёт следующим сообщением полную
   карточку товара (фото + caption + размеры + кнопка «↩️ К поиску»).

**Caption полной карточки товара:**

```
{⭐ Премиум | }🛍 {название}
Бренд: {brand}
Дроп: {drop_price}
Авито: {recommended_price}
📍 Город: {location_city}

{description}
```

**Кнопки в карточке:** все доступные размеры в формате `S · 3 шт` (где
`free = current_quantity - reserved_quantity`), потом `↩️ К поиску` —
возврат на промежуточное сообщение.

**Технические нюансы (для будущих итераций):**

- `cache_time: 30s` — Telegram кеширует inline-результаты, новые
  товары появляются с задержкой ~полминуты.
- Лимит результатов на страницу — 30, далее `next_offset` подгружает
  следующую пачку (Telegram сам).
- Старый категорийный flow удалён: `fetchCategories`,
  `fetchProductsByCategory`, `openCategory`, `findCategoryIndex`,
  `catalogCategories` сессия, callbacks `cat:idx:*`, `cat:pg:*`,
  `cat:back`, `↩️ К категориям`. Заменено на `searchProducts`,
  `fetchAvailableSizesByProductIds`, `openSearchPrompt`,
  `sendProductCard`, callback `customer:catalog`.
- История чата НЕ удаляется. Меню/каталог/wizard'ы используют
  `editMessageText` где можно (чисто, как у КиноПаба); транзакции
  (чек, статусы, уведомления) — отдельные сообщения, остаются как
  аудит-журнал клиента. Решение фазы 1 walkthrough'а экрана 3.
