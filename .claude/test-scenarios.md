# Сценарии тестирования

> Прогон сверху вниз. Цель — проверить, что система ведёт себя правильно
> в каждом бизнес-сценарии. Технические детали — в `handoff.md`.

## §0 Подготовка (один раз перед прогоном)

- [ ] **Карты владельца** в `/owner/payment-methods` — минимум одна,
      реквизиты реальные (Vision сравнивает чек с ними побуквенно).
- [ ] **Партнёр-1** привязан в `@krossovodpartnersbot`, реквизиты
      заполнены. В карточке `/owner/partners/<P1>`: «Город склада» =
      «Москва», «Принимает в долг» = ✅.
- [ ] **Партнёр-2** привязан, реквизиты заполнены. В карточке: город =
      «Питер», «Принимает в долг» = ❌.
- [ ] **Директор** привязан в `@doubleturtleassistantbot`.
- [ ] Тестовый клиент: баланс 0, без +ВАЙБ-долгов.
- [ ] Тестовый товар «Тест-50₽» создан через `/owner/products/new`: - Свой остаток: M=1, L=0, XL=0. - Лестница: #1 Партнёр-1 (склад его, комиссия 10₽, M=0 L=1 XL=0)
      → #2 Партнёр-2 (склад мой, комиссия 8₽, M=0 L=0 XL=2).
- [ ] `OPENAI_API_KEY` валиден (без него Vision сразу падает).

## §1 Лестница — кому уходят деньги и кто отгружает

Цель: один товар может продаваться сразу из нескольких источников. Кто
получает оплату и кто отгружает — зависит от того, какой по счёту
источник в лестнице активен и какой у него тип склада.

### 1.1 — Размер с моего склада (M)

**Что делает клиент:** заказывает M.
**Что должно произойти:** показываются мои реквизиты, клиент шлёт
чек, Vision подтверждает автоматически.

- [ ] В `/owner/orders/<id>` — пометка «🤖 Vision» (оплата принята автоматом).
- [ ] M на товаре теперь 0.
- [ ] Заказ виден в shipper-PWA — отгружает мой отправщик.

### 1.2 — Размер только у партнёра, склад его (L → Партнёр-1)

**Что делает клиент:** заказывает L.
**Что должно произойти:** мой L кончился → следующий по лестнице
Партнёр-1, склад у него → клиент платит партнёру → чек уходит ему в
Telegram.

- [ ] Реквизиты в боте — Партнёра-1.
- [ ] Партнёр-1 получает чек в `@krossovodpartnersbot` с подписью.
- [ ] Партнёр пишет «<номер> да» → заказ подтверждён.
- [ ] В `/owner/orders/<id>` — пометка «✋ partner».
- [ ] У Партнёра-1 размер L теперь 0.
- [ ] Заказ НЕ появляется в моём shipper-PWA — отгружает партнёр сам.

### 1.3 — Размер только у партнёра, но склад мой (XL → Партнёр-2)

**Что делает клиент:** заказывает XL.
**Что должно произойти (новая модель 2026-05-05 «деньги партнёру»):**
Партнёр-1 пустой → следующий Партнёр-2, склад у меня → клиент платит
**Партнёру-2** (по его реквизитам), Партнёр-2 подтверждает «N да»
текстом, отгружает мой отправщик. Партнёр-2 получил полную сумму, мне
причитается **комиссия от Партнёра-2** (запись в `partner_owner_debts`
через триггер на `is_paid=true`).

- [ ] Реквизиты в боте — Партнёра-2.
- [ ] Чек уходит Партнёру-2, Vision НЕ запускается.
- [ ] Партнёр-2 пишет «<номер> да» → заказ подтверждён.
- [ ] В `/owner/orders/<id>` — пометка «✋ partner» (не «🤖 Vision»).
- [ ] У Партнёра-2 «остаток у меня» XL уменьшился на 1.
- [ ] В `/owner/partners/<Партнёр-2>` блок «💰 Партнёр должен мне»
      вырастает на сумму комиссии этого заказа.
- [ ] Заказ ПОЯВЛЯЕТСЯ в моём shipper-PWA — отгружает мой отправщик
      (поскольку склад мой, а партнёр сам не отправляет).

### 1.4 — Каскад: партнёр сказал «у меня закончилось»

**Что делает партнёр:** на одном из заказов пишет «<N> нет → размер
закончился → ❌ Не пришли».
**Что должно произойти:** этот размер у партнёра обнулён, следующий
клиент по тому же размеру переходит к следующему партнёру (или ко
мне, если я тоже есть).

## §2 Автоматическая проверка чека (Vision)

Vision работает только когда оплата идёт ко мне (мой товар или
партнёрский с моим складом).

### 2.1 — Обычный чек принят автоматически

Клиент платит реальный чек → Vision проверяет 4 пункта (номер
операции уникален, сумма совпала, дата ≤24 часов, получатель = моя
карта/СБП/ИП) → подтверждает мгновенно. Клиенту: «✅ Заказ одобрен».

### 2.2 — PDF-чек

То же что 2.1, но клиент шлёт PDF (через «Поделиться чеком» → PDF).

### 2.3 — Vision не разобрал картинку → просим PDF

Клиент шлёт мутный/обрезанный/левый скриншот. Vision не находит
достаточно данных. Бот пишет «📌 Не получилось разобрать чек, пришли
PDF из приложения банка». Клиент шлёт PDF — система **автоматически**
принимает его как новую попытку (без жатия каких-либо кнопок).

### 2.4 — Vision не разобрал дважды → уходит к директору

Два мутных чека подряд. После второй неудачи чек попадает директору
на ручную проверку. Клиенту: «🔍 Заказ №N — отправили чек владельцу
на ручную проверку». Директору приходит чек с разбором по 4 пунктам.

### 2.5 — Чек с настоящим переводом, но не на нашу карту

Клиент случайно перевёл другому человеку и шлёт нам этот чек. Vision
видит чужого получателя:

> ⚠️ Получатель в чеке не совпадает с реквизитами оплаты.
> Что я увидел: карта в чеке ••XXXX.
> Перепроверь, что переводил по реквизитам выше, и пришли правильный чек.
> Если ты уверен, что перевод реально прошёл — напиши @{директор},
> разберёмся.
> Заказ №N ждёт оплаты.

### 2.6 — Тот же чек второй раз (anti-replay)

Клиент пытается прислать чек, который уже использовался для другого
заказа.

**Первая попытка:**

> ⚠️ Этот чек уже использован для заказа №X. Если ты ошибся — сделай
> новый перевод и пришли свежий чек. Если ты уверен, что перевод
> реально прошёл — напиши @{директор}, разберёмся.
> Заказ №B ждёт оплаты.

**Вторая попытка с тем же чеком:** уходит директору с пометкой
«подозрение на повторный чек», директор получает оба чека (новый +
оригинал из истории) для глазного сравнения.

**Безопасность:** даже если что-то пойдёт не так и проверка в коде
пропустит дубликат — БД на уровне UNIQUE-индекса не даст создать два
подтверждённых заказа с одним номером операции.

### 2.7 — Чек без видимого номера операции

На превью перевода в банк-приложении (а не на полноценном чеке) нет
номера операции. Vision это не пропускает:

> 📌 В чеке не виден номер операции — без него мы не можем подтвердить
> оплату. Открой операцию в банке → «Поделиться чеком» → выбери PDF
> и пришли сюда. На полноценном чеке номер операции есть всегда.
> Заказ №N ждёт оплаты.

### 2.8 — Чек старше 24 часов

Перевод сделан вчера, оформляешь сегодня:

> ⚠️ Чек старше суток — мы принимаем только переводы за последние 24 часа.
> Сделай новый перевод по реквизитам выше и пришли свежий чек.
> Если ты уверен, что перевод реально прошёл — напиши @{директор},
> разберёмся.
> Заказ №N ждёт оплаты.

## §3 Переплата

### 3.1 — Переплата до 300 ₽ — автоматически на баланс

Заказ 50 ₽, клиент перевёл 100 ₽. Vision подтверждает заказ, остаток
50 ₽ кладётся на баланс клиента.

### 3.2 — Переплата больше 300 ₽ → к директору

Заказ 50 ₽, клиент перевёл 5 000 ₽ (опечатка / Vision-галлюцинация).
Не подтверждаем автоматически — отдаём директору.

### 3.3 — Переплата при наличии +ВАЙБ-долга

Те же 100 ₽ за заказ 50 ₽, но у клиента есть +ВАЙБ-долг. Переплата
сначала гасит самые старые долги, остаток — на баланс.

## §4 Решения директора (когда чек ушёл на ручную проверку)

### 4.1 — Директор пишет «<номер> да»

Заказ подтверждён, в карточке заказа пометка «✋ director».

### 4.2 — Директор: «<номер> нет» → выбирает «💸 Деньги не пришли»

Заказ отменяется. Клиенту приходит DM с фиксированной причиной.

### 4.3 — «🟡 Сумма не совпала» → ввести фактическую сумму

Директор вводит «X ₽», подтверждает «✅ Да, применить».

- **X = ожидаемой** → подтвердить как обычный заказ.
- **X > ожидаемой** → подтвердить + переплата на баланс.
- **X < ожидаемой** → отменить заказ + положить X ₽ на баланс клиента.

### 4.4 — Защита от опечатки

Директор ввёл «9000» вместо «900». Бот спрашивает подтверждение с
явным diff («переплата 8 100 ₽») — даёт шанс «✏️ Изменить сумму».

## §5 Баланс клиента при оформлении

Работает только когда оплата идёт мне (мой товар или партнёрский с
моим складом).

### 5.1 — Баланса хватает на часть заказа

Баланс 200 ₽, заказ 900 ₽. Списываем 200 ₽ → клиенту реквизиты на
700 ₽. После оплаты — заказ подтверждён.

### 5.2 — Баланса хватает на весь заказ

Баланс 1 000 ₽, заказ 900 ₽. Списываем 900 ₽ → заказ подтверждается
мгновенно, реквизитов и таймера нет:

> ✅ Заказ №N оплачен полностью с баланса (900 ₽). Заказ в работе.

### 5.3 — Клиент отменил незавершённый заказ → баланс возвращается

Если клиент тапнул нижнее меню или нажал «❌ Отмена» когда часть
заказа была списана с баланса — баланс возвращается.

### 5.4 — Заказ протух за 10 минут → баланс возвращается

Если клиент не прислал чек за 10 минут — заказ автоматически
отменяется, баланс возвращается.

### 5.5 — +ВАЙБ-заказ + мой склад — баланс ПРИМЕНЯЕТСЯ

Решение 2026-05-06: для +ВАЙБ-заказов с моего склада сначала списываем
баланс, в долг идёт только остаток. Логика — это всё мои деньги, нет
смысла наращивать долг если на балансе есть средства.

Подсценарии в §8.12 (частичная) и §8.13 (полная оплата с баланса).

### 5.6 — Сумма в чеке меньше ожидаемой + был списан баланс

Директор вводит фактическую сумму X. X считается относительно
остатка после списания баланса, а не цены заказа.

### 5.7 — Заказ через партнёра со складом партнёра — баланс НЕ применяется

Заказ через Партнёра-1 (склад его). Деньги идут партнёру. Баланс
клиента не списываем — иначе пришлось бы платить партнёру с моих
денег.

### 5.8 — Заказ через партнёра со складом моим — баланс НЕ применяется

По новой модели «деньги партнёру для любого партнёрского» (2026-05-05):
даже если склад мой и отгружает мой shipper, оплачивает клиент
партнёру. Платить партнёру с моего баланса нельзя — это мои средства
клиенту. Баланс не трогаем, клиент целиком оплачивает партнёру по
реквизитам партнёра.

## §6 Отмена незавершённого заказа

Клиент в середине оформления тапает нижнее меню (📋 Каталог /
📦 Мои заказы / 👤 Профиль / 💳 Баланс / 🫂 Ассистент) — заказ
автоматически отменяется.

### 6.1 — Отмена в wizard'е до отправки чека

Клиент выбрал размер → ввёл доставку → ввёл трек → перед чеком
тапнул меню → заказ отменён, размер вернулся в наличие.

### 6.2 — Отмена в режиме «жду первый чек»

Аналогично — заказ отменён.

### 6.3 — Отмена когда первый чек был, но Vision не разобрал и ждём новый

Аналогично — заказ отменён.

### 6.4 — НЕ отменять, если чек уже на проверке

Защита от обмана «отменил пока проверяли чек». Если чек получен и
сейчас идёт обработка (Vision / директор / партнёр) — меню просто
открывается, заказ продолжает ждать.

### 6.5 — Возвраты не ломаются

Отмена касается только незавершённых заказов; уже завершённые /
возвращаемые — не трогаем.

## §7 Партнёр сказал «N нет»

Когда партнёр получает чек на свой склад и пишет «<N> нет», бот
спрашивает причину.

- **«оплата не пришла»** — без переспроса. Заказ отменяется.
- **«размер закончился»** или **«товар закончился»** — переспрос:
  «Деньги по чеку у тебя?» с двумя кнопками.

### 7.1 — «Оплата не пришла» (без переспроса)

- Заказ отменён, баланс клиента не трогаем, никаких долгов партнёра.
- Клиенту:
  > ❌ Заказ №N отменён. Партнёр сообщил, что оплата не пришла.
  > Если ты всё-таки перевёл — пиши @{директор}, разбираться будем
  > втроём. Контакт партнёра для справки: @P1.

### 7.2 — «Размер закончился» + ✅ Деньги пришли

- Заказ отменён.
- Деньги клиенту (вся сумма) → на баланс.
- Партнёр должен мне эту сумму (записывается в карточке партнёра в
  блок «💰 Партнёр должен мне»).
- Клиенту:
  > ❌ Заказ №N отменён — у партнёра закончился размер.
  > X ₽ зачислены на твой баланс — увидишь в «💼 Баланс».
- Партнёру:
  > Принял. Заказ №N отменён. За тобой числится долг владельцу X ₽ —
  > погасишь при следующем расчёте.
- Размер L у Партнёра-1 теперь 0 (на следующий заказ переходит к
  Партнёру-2 или мне).

### 7.3 — «Размер закончился» + ❌ Деньги не получал

- Заказ отменён.
- Никакого автокредита, баланс клиента не трогаем.
- Клиенту:
  > ❌ Заказ №N отменён. Партнёр сообщил, что размер закончился, и
  > оплаты он не получал. Если ты всё-таки перевёл — пиши @{директор},
  > разбираться будем втроём. Контакт партнёра для справки: @P1.
- Размер L у Партнёра-1 теперь 0.

### 7.4 — «Товар закончился» + ✅ Деньги пришли

Аналог 7.2 (но «закончился вообще», не только этот размер).

### 7.5 — «Товар закончился» + ❌ Деньги не получал

Аналог 7.3.

### 7.6 — Бот понимает разные формулировки причины

- Краткие: «оплата» / «размер» / «товар» — работают.
- Регистр не важен.
- Непонятный текст → бот: «Не понял. Напиши одно из…»

### 7.7 — Кнопка «Получил» в карточке партнёра

В `/owner/partners/<P1>` блок «💰 Партнёр должен мне» — кнопка
«Получил» рядом с долгом. Тап → долг помечен погашенным.

## §8 +ВАЙБ-клиенты (работа в долг)

+ВАЙБ-клиент = клиент с разрешением заказывать в долг. Долг копится
отдельно от баланса, оплачивается через «💳 Оплатить долг».

### 8.1 — +ВАЙБ-клиент + мой товар → мгновенно в долг

Клиент тапает M (мой склад) → заказ оформляется мгновенно как долг,
без чека и таймера.

> ✅ Заказ №N принят в долг. Товар уходит в сборку…

Карточка заказа в группе клиентов появляется немедленно.

### 8.2 — +ВАЙБ-клиент + партнёр-склад + Партнёр-1 (принимает в долг)

Клиент тапает L → партнёру DM:

> 🛍 Заказ в долг №N. Можешь отправить?

(без чека).

Партнёр пишет «<N> да» → заказ оформлен как долг. Клиент гасит долг
позже через «💳 Оплатить долг».

### 8.3 — +ВАЙБ-клиент + партнёр-склад + партнёр НЕ работает в долг

(Создать тестового Партнёра-3 — склад его, «Принимает в долг» = ❌.)

Клиент тапает размер → wizard показывает предупреждение:

> ⚠️ Размер X «{товар}» сейчас идёт от партнёра «{имя}» — он не
> работает в долг. Можно оформить только обычной оплатой (не «+ВАЙБ»).

Кнопки: [✅ Оформить обычной оплатой] [❌ Отмена].

- ✅ → обычный заказ с реквизитами партнёра, чек, всё как у не-+ВАЙБ.
- ❌ → размер освобождён, главное меню.

### 8.4 — +ВАЙБ-клиент + Партнёр-2 (склад мой) — без предупреждения

Клиент тапает XL → склад мой → платит мне → мгновенно в долг (как
8.1). Настройка «Принимает в долг» партнёра не важна — деньги идут
мне.

### 8.5 — Выдача +ВАЙБ из карточки клиента (DM-экскурс)

**Что делает владелец:** в `/owner/clients/<id>` включает «+ВАЙБ»
тумблером.

**Что должно произойти:**

- [ ] У клиента в БД `vibe_enabled=true`.
- [ ] Клиенту приходит DM: > 🎉 Тебе открыли «+ВАЙБ» — статус, который позволяет заказывать в долг. > > Что это даёт: > • Оформляешь заказ — товар сразу уходит в сборку, не ждём чек. > • Долг копится по каждому заказу. Гасишь когда удобно через «💳 Оплатить долг» в главном меню. > • Лимит долга — **{X} ₽**. Когда упрёшься — оформление новых заказов приостановится до погашения. > > ⚠️ Не на всё работает: партнёрские товары, у которых партнёр не работает в долг, придётся оформлять обычной оплатой. Бот тебя предупредит на этапе выбора размера. > > Если что — пиши @{директор}, разберёмся.
- [ ] Лимит **{X}** = индивидуальный override клиента, если задан, иначе
      `business_settings.vibe_credit_default_limit`.

### 8.6 — Изменение лимита +ВАЙБ — увеличение

**Что делает владелец:** меняет персональный лимит клиенту с 50 000 ₽
на 150 000 ₽.

- [ ] В БД `vibe_credit_limit_override = 150000`.
- [ ] Клиенту DM: > 📊 Твой лимит «+ВАЙБ» изменили: ~~50 000 ₽~~ → **150 000 ₽**. > > Теперь можешь оформлять заказы в долг до этой суммы.

### 8.7 — Изменение лимита +ВАЙБ — уменьшение

**Что делает владелец:** меняет лимит с 150 000 ₽ на 50 000 ₽.

- [ ] В БД `vibe_credit_limit_override = 50000`.
- [ ] Клиенту DM: > 📊 Твой лимит «+ВАЙБ» изменили: ~~150 000 ₽~~ → **50 000 ₽**. > > Если текущий долг превышает новый лимит — оформление новых заказов приостановится до погашения.
- [ ] Если **текущий долг > нового лимита** — триггер
      `check_vibe_credit_freeze` автоматически выставляет
      `is_frozen=true, frozen_reason='auto_limit_exceeded'`.

### 8.8 — Снятие +ВАЙБ при долге = 0

**Что делает владелец:** у клиента долга нет, выключает «+ВАЙБ»
тумблером.

- [ ] В БД `vibe_enabled=false`.
- [ ] `is_frozen` остаётся false (никто не замораживает).
- [ ] Клиенту DM: > 📊 С тебя сняли «+ВАЙБ». > > Теперь заказы оформляются только обычной оплатой — товар уходит в сборку после подтверждения чека.
- [ ] Клиент может оформлять новые заказы обычной оплатой.

### 8.9 — Снятие +ВАЙБ при наличии долга → автозаморозка

**Что делает владелец:** у клиента долг 30 000 ₽, выключает «+ВАЙБ».

- [ ] В БД `vibe_enabled=false`.
- [ ] **`is_frozen=true`** автоматически.
      `frozen_reason='vibe_revoked_with_debt'`.
      `required_payment_amount=NULL` (порог не задан → разморозка только при долге=0).
      `frozen_debt_snapshot=30000` (заполняется триггером).
- [ ] Клиенту DM с inline-кнопкой «💳 Оплатить долг»: > 📊 С тебя сняли «+ВАЙБ». Текущий долг — **30 000 ₽**. > > До его полного погашения оформление новых заказов приостановлено. Как только долг закроется — снова можно оформлять (обычной оплатой).
- [ ] Клиент пытается оформить новый заказ → блок с прогрессом и
      inline-кнопкой «💳 Оплатить долг».
- [ ] Клиент гасит долг полностью → триггер авторазмораживает:
      `is_frozen=false`, `frozen_reason=null`, `required_payment_amount=null`,
      `frozen_debt_snapshot=null`. DM «Долг оплачен, аккаунт разморожен».
- [ ] После разморозки клиент может оформлять обычные заказы (без +ВАЙБ).

### 8.10 — Fallback по лимиту (мой склад)

+ВАЙБ-клиент, лимит 5 000 ₽, текущий долг 0, оформляет заказ на 8 000 ₽.

- [ ] Бот: > ⚠️ Заказ не влезает в лимит «+ВАЙБ» (твой лимит: 5 000 ₽, текущий долг: 0 ₽, заказ: 8 000 ₽).\n\nОформляем обычной оплатой — пришли чек по реквизитам ниже.
- [ ] Дальше идёт обычный flow с чеком (10-минутный таймер, реквизиты владельца, Vision).
- [ ] Клиент **НЕ замораживается**, `vibe_enabled` остаётся true.
- [ ] В `pending_orders.is_vibe_debt=false`, при confirm — обычный заказ,
      `payment_method='card'`.

### 8.11 — Fallback по лимиту (склад партнёра, партнёр-в-долг)

То же самое, но размер у партнёра-warehouse + `accepts_vibe_debt=true`.

- [ ] Тот же текст «не влезает в лимит → обычной оплатой».
- [ ] Реквизиты партнёра, чек партнёру, партнёр подтверждает «N да».
- [ ] `pending_orders.is_vibe_debt=false`.

### 8.12 — Частичная оплата балансом при +ВАЙБ-заказе

+ВАЙБ-клиент, баланс 3 000 ₽, лимит 100 000 ₽, заказ 10 000 ₽ (мой склад).

- [ ] В `pending_orders`: `applied_balance=3000`, `is_vibe_debt=true`.
- [ ] При instant confirm — `orders.applied_balance=3000`, `is_paid=false`,
      `payment_method='deposit'`.
- [ ] Долг по этому заказу = `client_price - applied_balance = 7000 ₽`.
- [ ] Клиенту DM: > ✅ Заказ №N принят.\n💼 С баланса списано 3 000 ₽, в долг ушло 7 000 ₽.\n\nТовар уходит в сборку — отправку подтвердим в боте.
- [ ] `customers.customer_balance=0`, в `customer_balance_history` запись `'balance_apply'` на −3 000.

### 8.13 — Полная оплата балансом при +ВАЙБ-заказе

+ВАЙБ-клиент, баланс 15 000 ₽, заказ 10 000 ₽ (мой склад).

- [ ] В `pending_orders`: `applied_balance=10000`, `fully_paid_by_balance=true`.
- [ ] При confirm — `orders.is_paid=TRUE`, `payment_method='balance'`,
      `applied_balance=10000`. То есть заказ НЕ долговый.
- [ ] Клиенту DM: > ✅ Заказ №N оплачен полностью с баланса (10 000 ₽).\n\nТовар уходит в сборку — отправку подтвердим в боте.
- [ ] `customer_balance=5000` после операции.
- [ ] В долге этот заказ НЕ светится (он сразу оплачен).

### 8.14 — Ручная заморозка с порогом

**Что делает владелец:** в `/owner/clients/<id>` нажимает 🔒 Заморозить →
снимает чекбокс «требовать оплатить весь долг» → вводит порог 10 000 ₽ →
причина (например, «Просрочка») → подтверждает.

У клиента текущий долг 30 000 ₽.

- [ ] В БД: `is_frozen=true`, `frozen_reason='manual'`,
      `required_payment_amount=10000`, `frozen_debt_snapshot=30000`,
      `frozen_at=NOW()`.
- [ ] В `activity_log` запись `customer_freeze`.
- [ ] Клиенту DM с inline-кнопкой «💳 Оплатить долг»: > 🔒 Твой аккаунт временно заморожен.\n\nТекущий долг: **30 000 ₽**\nНужно оплатить больше чем: **10 000 ₽**\n\nЧтобы продолжить оформлять заказы — погаси долг.
- [ ] Клиент тапает размер → блок с прогрессом и inline-кнопкой: > 🚫 Ваш аккаунт временно заморожен.\n\nНужно оплатить больше чем 10 000 ₽.\nУже оплачено: 0 ₽.\nОсталось до разморозки: 10 000 ₽.

### 8.15 — Частичное погашение с прогрессом в DM

Замороженный клиент (porog 10 000, snapshot 30 000) гасит через wizard
заказы на 4 000 ₽ → Vision подтверждает.

- [ ] Триггер пересчитывает: `paid_since_freeze = 30000 − 26000 = 4000 < 10000` →
      остаётся `is_frozen=true`.
- [ ] Клиенту DM: > ✅ Оплата **4 000 ₽** принята.\n\n📊 До разморозки: оплачено **4 000 ₽** из **10 000 ₽**, осталось **6 000 ₽**.

### 8.16 — Достаточное погашение → авторазморозка

Тот же клиент гасит ещё на 7 000 ₽ → Vision подтверждает.

- [ ] Триггер: `paid_since_freeze = 30000 − 19000 = 11000 ≥ 10000` →
      `is_frozen=false`, всё zero'нуто (`required_payment_amount=null`,
      `frozen_reason=null`, `frozen_debt_snapshot=null`).
- [ ] Клиенту прилетает ДВА DM подряд: 1. > ✅ Оплата **7 000 ₽** принята. (без блока прогресса — клиент уже размо
      рожен на этот момент) 2. > ✅ Долг оплачен, аккаунт разморожен. Можно снова оформлять заказы!
- [ ] Клиент может оформлять новые заказы (если +ВАЙБ остался — снова в долг).

### 8.17 — Ручная разморозка из owner-panel

**Что делает владелец:** в `/owner/clients/<id>` у замороженного клиента
нажимает 🔓 Разморозить → подтверждает диалог.

- [ ] В БД: `is_frozen=false`, `frozen_at=null`, `frozen_reason=null`,
      `required_payment_amount=null`, `frozen_debt_snapshot=null`.
      Долг при этом остаётся прежним (разморозка ≠ списание долга).
- [ ] Клиенту DM: > ✅ Долг оплачен, аккаунт разморожен. Можно снова оформлять заказы!
      (текст немного некорректен для случая «разморозили вручную при долге»,
      но как минимальная индикация — OK)
- [ ] Клиент сразу может оформлять заказы.

### 8.18 — partner_owner_debts при погашении +ВАЙБ-партнёрского

+ВАЙБ-клиент оформляет партнёрский заказ (партнёр-в-долг, склад его) →
партнёр пишет «N да» → заказ создан `is_paid=false`,
`payment_method='deposit'`, `partner_commission_snapshot=X`.

- [ ] В этот момент в `partner_owner_debts` для этого order_id **ничего нет**
      (раньше было — теперь нет).
- [ ] В `/owner/partners/<id>` блок «💰 Партнёр должен мне» **не растёт**
      на эту комиссию.

Затем клиент гасит долг через wizard «💳 Оплатить долг» — выбирает
партнёрскую группу → partner-bot ждёт чек → клиент шлёт чек партнёру →
партнёр пишет «N да».

- [ ] `orders.is_paid=true`, `payment_method` (становится 'card' или
      сохраняется 'deposit' — проверить, как partner-bot обновляет).
- [ ] Триггер `trg_partner_debt_on_vibe_payment` пишет
      `partner_owner_debts(reason='partner_commission')` на сумму
      `partner_commission_snapshot`.
- [ ] В `/owner/partners/<id>` блок «💰 Партнёр должен мне» вырастает
      на эту комиссию.

## §9 Заказ ждёт оплаты дольше суток

Когда чек ушёл к директору на ручную проверку и директор молчит, есть
автозащита: через 24 часа заказ автоматически отменяется.

### 9.1 — Директор молчит 24 часа → автоотмена

- Pending удалён.
- Клиенту: «❌ Заказ №N отменён. Чек так и не подтвердили за сутки.»
- Владельцу приходит уведомление об эскалации.
- В `/owner/orders` заказ помечен как cancelled.

### 9.2 — Директор подтвердил до 24 часов → автоотмена не срабатывает

Если директор успел нажать «N да» / «N нет» — таймер не срабатывает.

### 9.3 — Защита от потерянного таймера

Даже если технический таймер потерялся при перезапуске — каждую
минуту проверяется список заказов старше 24h, и они автоматически
закрываются.

## §10 UI и тексты

### 10.1 — Карты владельца (`/owner/payment-methods`)

- **Card / СБП:** обязательны «Держатель» и «Банк».
- **ИП-QR:** обязательно «Наименование ИП», фото QR.
- Жёлтое предупреждение, что эти поля сравниваются с чеком побуквенно
  (если ошибиться — все чеки будут уходить директору на ручную
  проверку).
- Кнопка «Удалить» — настоящий DELETE (история сохраняется через FK).
- Кнопка «Отключить/Включить» — soft-toggle.

### 10.2 — Создание / редактирование товара

- Секция «🤝 Партнёры в очереди» с кнопкой «+ Подключить партнёра».
- Drag перетаскивает карточку — приоритет меняется. Сохранение →
  новый порядок в БД.
- Каждая карточка: партнёр, тип склада (📦 У меня / 🤝 У него),
  комиссия, таблица размеров.
- Для one-size товара тоже видна таблица «One Size · сколько у
  партнёра».
- Удаление партнёра из очереди — если у него были активные заказы,
  binding помечается как удалённый (но текущие заказы дорабатываются).

### 10.3 — Карточка товара (`/owner/products/[id]`)

3 статуса (бейджа):

- **🟢 «В наличии»** — есть сток у меня ИЛИ у пригодного партнёра.
- **🟡 «В пути»** — стока нет, но указана дата приезда.
- **🔴 «Распродан»** — стока нет нигде, дата приезда не указана.

«Пригодный партнёр» = активен И (склад мой ИЛИ есть реквизиты для
склада партнёра).

Под блоком цен — список «🤝 Партнёры в очереди» с приоритетами и
комиссиями.

### 10.4 — Карточка партнёра (`/owner/partners/[id]`)

- Поле **«Город склада» обязательное** (NOT NULL в БД с 2026-05-06).
  Показывается клиенту в боте при выборе размера у этого партнёра
  («🏙️ Город: …») и в карточке заказа.
- При создании партнёра в `/owner/partners` модалка тоже требует
  заполнить город (кнопка «Создать» disabled пока город пустой).
- Чекбокс «Принимает заказы в долг».
- Блок «👑 Я должен партнёру» — старая логика commissionOwed.
- Блок «💰 Партнёр должен мне» — список долгов, кнопка «Получил» →
  погашение. Пишется автоматически:
  - для не-+ВАЙБ-партнёрских заказов — при confirm_pending (партнёр
    получил оплату от клиента),
  - для +ВАЙБ-партнёрских — при погашении +ВАЙБ-долга через wizard
    (триггер на `orders.is_paid=true`).

### 10.5 — Тексты бота при оформлении заказа

- **Не +ВАЙБ, баланс 0:**
  > ⏳ Заказ №N ожидает оплаты — у тебя 10 минут на чек по реквизитам
  > ниже.
- **Не +ВАЙБ, баланс частичный:**
  > 💼 С баланса списано X ₽.
  > ⏳ Заказ №N — к оплате осталось Y ₽…
- **Не +ВАЙБ, баланс полный (instant balance-paid):**
  > ✅ Заказ №N оплачен полностью с баланса (X ₽). Заказ в работе.
- **+ВАЙБ + мой склад, без баланса:**
  > ✅ Заказ №N принят в долг.
  >
  > Собираем — пришлём уведомление, как только отправим.
- **+ВАЙБ + мой склад, частичный баланс:**
  > ✅ Заказ №N принят.
  > 💼 С баланса списано X ₽, в долг ушло Y ₽.
  >
  > Собираем — пришлём уведомление, как только отправим.
- **+ВАЙБ + мой склад, полный баланс:**
  > ✅ Заказ №N оплачен полностью с баланса (X ₽).
  >
  > Собираем — пришлём уведомление, как только отправим.
- **+ВАЙБ + партнёр-склад:**
  > ✅ Заказ №N — отправили партнёру на подтверждение наличия.
  >
  > Обычно отвечают в течение нескольких часов; крайний срок — 24 часа.

### 10.6 — Тексты при получении чека

- **Мой склад:**
  > 🧾 Чек получен — проверяем оплату. Напишем как только подтвердим.
- **Склад партнёра:**
  > 🧾 Чек получен — пересылаем партнёру на подтверждение.

### 10.7 — Текст «не ждём чек ни по какому заказу»

Если клиент шлёт фото или PDF, когда у него нет активного заказа:

> 🤔 Сейчас мы не ждём чек ни по одному из твоих заказов.
>
> Если ты перевёл деньги по оформленному заказу, но он куда-то исчез —
> напиши @{директор}, разберёмся со суммой.

Логика handle:

1. Если директор привязан → его личный @username.
2. Если нет — fallback на личный @username владельца.
3. Если ни того ни другого нет — строка про связь не показывается.

### 10.8 — Карточка товара в каталоге бота

Размер показывается с **суммарным** количеством (мой склад +
партнёрский). Если у меня 0 и у партнёра 5 — кнопка «M · 5 шт» (а не
«M · 0 шт»).

## §11 Расписание сводок директору и партнёрам

В `/owner/settings → ⏰ Расписание сводок` две строчки (директор и
партнёры). У каждой — окно работы (start/end в МСК) и шаг (1/2/3/4/6
часов). Под формой preview: «придёт в HH:00 · HH:00 · …», обновляется
на лету.

### 11.1 — Дефолтные настройки

По дефолту обе настройки 10:00–22:00 МСК, шаг 3ч. Preview:
«10:00 · 13:00 · 16:00 · 19:00 · 22:00».

### 11.2 — Изменение шага директора с 3ч на 2ч

Preview сразу пересчитался на «10:00 · 12:00 · 14:00 · 16:00 · 18:00 ·
20:00 · 22:00». Сохранение → новые значения видны в read-view.

### 11.3 — Изменение окна партнёра на 11:00–23:00 (шаг 3ч)

Preview «11:00 · 14:00 · 17:00 · 20:00 · 23:00». Сохранение →
применяется.

### 11.4 — Изменения применяются на следующем часовом тике

Никаких рестартов сервера не требуется. На ближайшем часовом «00»
(например 14:00, 15:00 — любой ровный час в окне) сводка приходит
по новой настройке.

### 11.5 — Тики вне окна — тишина

Окно 14:00–18:00 шаг 1: до 14:00 и после 18:00 уведомлений нет.

### 11.6 — Очередь пустая → даже на «должном» часе тишина

Если нет неподтверждённых чеков — сообщение не приходит.

### 11.7 — Дубликаты не плодятся при рестартах

После 3 перезапусков `dev:all` подряд расписание остаётся одно. В
логах одна запись «Scheduled director-receipts-digest hourly».

### 11.8 — Партнёрский digest независим от директорского

Окно директора 10:00–22:00 шаг 3, окно партнёра 12:00–20:00 шаг 2.
Каждый ходит по своему расписанию, не мешая другому.

### 11.9 — Зависшие 24h+ заказы больше не висят

Даже если технический таймер потерян — фоновая проверка каждую
минуту смотрит на заказы старше 24h и сама их закрывает.

## §12 Регрессии (на всякий случай)

- **Race на размере:** два клиента одновременно тапают единственный
  мой сток → один получает «Размер закончился».
- **Возврат партнёрского размера:** при `return_done` для partner-source —
  сток возвращается у нужного партнёра.
- **Партнёр выключен (is_active = false):** его сток исчезает из
  каталога и из расчёта «в наличии».
- **Партнёр без реквизитов** (склад его): сток не учитывается (клиент
  не сможет ему заплатить, поэтому его «как будто нет»).
- **Owner редактирует размер ниже зарезервированного:** новые заказы
  не проходят, текущие — дорабатываются.
- **Удаление партнёрского binding'а с активным pending:** binding
  soft-delete, заказ дорабатывается.
- **Shipper PWA только мои заказы:** заказы со складом партнёра не
  появляются в `/shipper/queue`.
- **Anti-replay 100%:** один и тот же чек никогда не подтверждает два
  заказа (защита и в коде, и на уровне БД UNIQUE-индексом).
- **One-size товар + партнёрский сток:** редактор показывает инпут
  «One Size · …» в каждом блоке партнёра; статус правильно учитывает
  партнёрский сток.
