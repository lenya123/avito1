## 1. О проекте

**B2B SaaS-коробка для оптовиков одежды.** Single-tenant: один деплой
на одного оптовика. Продаётся индивидуально, кастомизация через `.env`
и `business_settings`.

**Клиенты оптовика — дропшипперы.** Перепродают на Авито. У нас от них
только трек-номер от Авито/выбранной службы. Адрес/ПВЗ конечного
получателя в системе **не хранится никогда**.

## 2. Роли

| Роль          | Кто                                                     | Канал работы                         |
| ------------- | ------------------------------------------------------- | ------------------------------------ |
| **Владелец**  | Оптовик (наш клиент-покупатель SaaS)                    | `/owner/*` web-панель + DM owner-bot |
| **Отправщик** | Сотрудник владельца (один из нескольких)                | shipper-PWA + DM shipper-bot         |
| **Клиент**    | Дропшиппер, перепродающий на Авито                      | DM customer-bot                      |
| **Партнёр**   | Другой оптовик, чьи товары владелец продаёт за комиссию | DM partner-bot                       |

Конечный покупатель на Авито **не является ролью** — про него ничего
не знаем.

## 3. Бот-архитектура

| Бот              | Роль                      | Где общается                                     |
| ---------------- | ------------------------- | ------------------------------------------------ |
| **customer-bot** | Клиенты + публичные посты | DM с клиентами + клиентская группа + ЧЕКИ-группа |
| **partner-bot**  | Партнёры                  | Только DM                                        |
| **owner-bot**    | DM-алерты владельцу       | Только 1:1 с владельцем, нигде в группах         |
| **shipper-bot**  | Отправщики                | Только DM                                        |

**Owner-bot — «секретный»:** непредсказуемый username, нигде в группах
не светится. Все group-посты идут через customer-bot.

## 4. Жизнь заказа

### 4.1 Принципы

Поток оформления **разный** для не-+ВАЙБ и +ВАЙБ-клиента (с 2026-05-01).

#### Ветка А — обычный клиент (не-+ВАЙБ, дефолт)

- **В `orders` запись появляется ТОЛЬКО после подтверждения оплаты.**
  До этого живёт `pending_orders` с TTL 10 мин (`expire-pending-order`).
  Wizard → `create_pending_order_atomic` создаёт `pending_orders`-row
  с уже выделенным `order_number` из sequence и инкрементом
  `reserved_quantity`. Если за 10 мин чек не пришёл — `cancel_pending_*`
  чистит pending и возвращает резерв.
- **Чек от клиента → Vision auto-confirm** (см. §8). При успехе
  `confirm_pending_order_atomic` создаёт `orders`-row с тем же
  `order_number`, `status='paid'`, `is_paid=true`. При ошибке Vision —
  эскалация директору, текстовое подтверждение.
- **Применение баланса при оформлении.** `create_pending_order_atomic`
  автоматически вычитает `min(customer_balance, client_price)` →
  `pending_orders.applied_balance`. Если баланс полностью покрыл
  стоимость — `confirm_pending_order_atomic` зовётся сразу без чека,
  заказ с `payment_method='balance'`. При cancel/expire — баланс
  возвращается.

#### Ветка Б — +ВАЙБ-клиент

- **Заказ сразу в `orders` со `status='paid'`, `is_paid=false`.**
  Vision не запускается — это кредит. `is_paid=true` поставится позже,
  когда клиент погасит долг через wizard оплаты долга (§7.4).

#### Общие принципы

- **Защита от двойной продажи — атомарная.** RPC использует
  `SELECT ... FOR UPDATE` на `product_sizes`, сериализуя параллельные
  оформления одного размера. Параллельный второй клиент получает
  `OUT_OF_STOCK` exception.
- **Soft-резерв на время wizard'а.** При тапе на размер
  `reserve_size_atomic` инкрементит `reserved_quantity` в TTL 10 мин.
  BullMQ-job `release-reservation` авто-снимает резерв если оформление
  не подтверждено.
- **«Отправлен» = финальный успешный.** Никаких «в пути / доставлено».
- **Возврат — смена статуса того же заказа,** не новая сущность.
- **Один заказ = одна позиция** (корзины нет — трек один на отправление).
- **Скоуп — клиентские заказы.** Заказы из Авито-магазинов владельца —
  отдельный поток (фаза 3).

### 4.2 Статусы

8 канонических статусов (после слияния enum'ов 2026-04-28) + 3
Авито-only статуса для `source='avito'` (`awaiting_size`, `delivered`,
`return_in_transit` — см. §15.2). Печать стикера — внутрянка отправщика
(флаг `barcode_printed`), не статус.

| Статус        | Описание                              | Терминальный?            |
| ------------- | ------------------------------------- | ------------------------ |
| `paid`        | Оплачен / оформлен (общий пул)        | Нет                      |
| `collecting`  | Взят отправщиком в работу             | Нет (живёт до 00:00 МСК) |
| `sent`        | Сдан в ПВЗ службы                     | Да (успешный)            |
| `return`      | Клиент оформил возврат                | Нет                      |
| `return_done` | Возврат принят отправщиком/партнёром  | Да (успешный возврат)    |
| `trash`       | `pickup_by` истёк, возврат не забрали | Условно (1 переоткрытие) |
| `cancelled`   | Отменён до отправки                   | Да                       |
| `problem`     | Товар отсутствует на складе           | Нет (ждёт поступления)   |

### 4.3 Принадлежность заказа отправщику

Поле `claimed_by` (единственное; `assigned_shipper_id` выпилен
2026-05-16, миграция `20260516000050`):

- `paid` → NULL (общий пул, виден всем отправщикам).
- `collecting` → конкретный отправщик.
- `sent`, `return_done`, `trash` → исторический (для рейтинга/выплат).
  При `sent` дополнительно пишется `shipped_by` (= исполнитель) и
  снапшот ставки `shipper_rate_snapshot` (§9.4).

Имя отправщика **никогда не показывается клиенту** в боте. Внутренняя кухня.

### 4.4 Переходы

> Авито-only переходы — см. §15.4.

```
paid → collecting           отправщик жмёт «Беру в работу»
paid → cancelled            клиент жмёт «Отменить» / send_by сгорел
paid → problem              отправщик жмёт «Проблема: нет товара» / «Трек не сканируется»

collecting → sent           отправщик жмёт «Сдал в ПВЗ»
collecting → paid           00:00 МСК если не довёл до sent (auto, daily-shipper-cleanup)
collecting → cancelled      send_by сгорел / клиент отменил
collecting → problem        отправщик жмёт «Проблема: нет товара» / «Трек не сканируется»

problem → collecting        пришёл возврат другого заказа на этот SKU+размер
                            ИЛИ владелец вручную пополнил остаток
problem → cancelled         send_by сгорел до восстановления товара

sent → return               клиент в боте оформил возврат

return → return_done        отправщик/партнёр жмёт «✅ Забран и в порядке»
return → sent               клиент жмёт «Отменить возврат» (до первой попытки забора)
return → trash              pickup_by истёк (auto)

trash → return              клиент жмёт «Переоткрыть возврат» (1 раз, если return_attempts_count<2)
```

**ПВЗ при «Сдал в ПВЗ» — адрес-снимок, без связи** (решение 2026-05-15).
Отправщик выбирает пункт выдачи из справочника `pickup_points` (его он
ведёт сам в Shipper PWA: добавляет/удаляет адреса по службам). В заказ
пишется **текстовый снимок** `pickup_point_label_snapshot` (служба) +
`pickup_point_address_snapshot` (адрес) — устойчив к последующему
удалению/правке адреса в справочнике (история не ломается). FK у
`orders.pickup_point_id` НЕТ (нестрогая ссылка). Можно сдать и «без
ПВЗ» (снимок пуст). Таблица `shipper_pickup_points` удалена как мёртвая.

### 4.5 Дедлайны

**`send_by`** — клиент задаёт при оформлении заказа.

- **Формат:** inline-календарь в боте.
- **Минимум:** сегодня (если сейчас раньше `business_settings.send_by_today_cutoff`,
  дефолт `16:00 МСК`) или завтра (после cutoff).
- **Максимум:** `business_settings.send_by_max_days` (дефолт 7 дней).
- **Дефолт открытия календаря:** +2-3 дня.
- **Редактируется:** клиентом в «Мои заказы» в `paid` или `collecting`,
  в любую сторону в пределах окна. После `sent` редактирование закрыто
  (печать стикера — флаг `barcode_printed`, не статус и не гейт, см. 4.2).
- **Сгорание:** статус → `cancelled`, баланс клиента пополняется
  (см. 9.2).

**`pickup_by`** — клиент задаёт при оформлении возврата.

- **Формат:** inline-календарь.
- **Минимум:** сегодня. **Максимум:** `business_settings.pickup_by_max_days`
  (дефолт 14 дней). **Дефолт открытия:** +7 дней.
- **Редактируется:** в карточке возврата.
- **Сгорание:** статус → `trash` + определяется fault (см. 6.4).

### 4.6 Таймеры на отправщиков (00:00 МСК)

Ежедневный job `daily-shipper-cleanup` в 00:00 МСК:

- Все `collecting` без `sent` → `paid`. Отправщик взял в работу, но не
  довёл до сдачи в ПВЗ в день взятия. Флаг `barcode_printed` сбрасывается
  (печать — не статус, см. 4.2).

`claimed_by` сбрасывается, заказ возвращается в общий пул. DM только
**отправщику-исполнителю** (его заказы, actionable: «возьми заново из
общего пула»). Владельцу/директору DM **не шлётся**: сигнал
«незавершённые сборки» постоянно отражён в KPI карточки отправщика
(§9.5 метрика 2) — ночной агрегат-пинг бесполезен (решение 2026-05-16).

Срабатывает **независимо от длительности** работы. Заказ взят в 23:50 →
если до 00:00 не дошёл до `sent` — откатывается через 10 минут. Это
правило фиксированное, не таймер «N часов от взятия».

## 5. Wizard оформления заказа

Запускается из «🛍 Каталог» (выбор товара) или из «📦 Мои заказы» →
«Заказать ещё раз».

### 5.1 Шаги

1. **Товар** — клиент выбрал из каталога/поиска или из истории.
2. **Размер** — кнопкой. Размеры со `stock=0` неактивны.
3. **Служба доставки** — Яндекс / СДЭК / Почта России / Авито Доставка
   / 5post. Дефолт из профиля.
4. **Трек-номер** — текстом. Без трека дальше нельзя.
5. **`send_by`** — inline-календарь (см. 4.5).
6. **Реквизиты для оплаты:**
   - Свой товар → реквизиты владельца через `next_payment_method(amount)`.
   - Партнёрский товар → статичные реквизиты партнёра из
     `partners.payment_requisites` (текст или QR-фото). См. §10.2.
   - Сумма — `client_price`.
   - Если клиент с `vibe_enabled=true` и не заморожен — рядом
     дополнительная кнопка **«Оплатить позже (+ВАЙБ)»**.
7. **Чек или +ВАЙБ:**
   - «Оплатить позже» → заказ создаётся **сразу** в `paid` с
     `is_paid=false` (флаг +ВАЙБ-долга). Vision не запускается.
   - Фото чека → Vision auto-confirm (см. 8). При успехе → заказ
     создаётся в `paid`. При неуспехе → отказ с причиной, wizard
     остаётся на шаге чека (лимит 5 попыток на сессию).

### 5.2 +ВАЙБ-нюанс

Заказ через «Оплатить позже» создаётся **даже если** новый долг
превысит лимит. Никаких отказов в wizard-е. Заморозка срабатывает
**после** создания заказа: триггер `check_vibe_credit_freeze`
пересчитает долг → если > лимит → `is_frozen=true` → клиенту
уведомление через `notifyCustomerVibeFrozen`. В следующий wizard
кнопка «Оплатить позже» уже не показывается.

### 5.3 Прерывание

В любой момент клиент может:

- Нажать `/menu` → wizard сбрасывается (заказа в БД ещё нет).
- Не отвечать → grammy session истекает.
- 5 неуспешных Vision-попыток → wizard закрывается с просьбой связаться
  с владельцем.

## 6. Возвраты

### 6.1 Кто инициирует

Только **клиент-дропшиппер** в боте. Конечный покупатель с системой не
связан, отправщик/владелец возврат не инициируют.

### 6.2 Когда доступна кнопка «Оформить возврат» в боте

- В `sent` (первый возврат).
- В `trash` если `return_attempts_count < 2` (переоткрытие).

Не доступна: в `return`, `return_done`, `trash` после 2 циклов,
`cancelled`.

### 6.3 Wizard оформления возврата

1. **Трек возврата** — текстом.
2. **Код возврата** — текстом. Указывается **для всех заказов** (своих
   и партнёрских). Для партнёрских клиент дополнительно сам шлёт код
   партнёру в DM — но в нашей системе код хранится в любом случае
   (нужен для wrong_code-результата на ПВЗ).
3. **`pickup_by`** — inline-календарь (см. 4.5).
4. **Подтверждение** → заказ → `return`. `return_attempts_count++`.

**Отмена возврата** клиентом доступна **до первой попытки забора** (нет
ни одной записи в `return_pickup_attempts`). Заказ возвращается в
`sent`. `return_attempts_count` **не сбрасывается** — оформление+отмена
тратят 1 цикл из лимита 2.

**Переоткрытие из `trash`** — полный wizard заново, новые трек/код/pickup_by.
`return_attempts_count := 2`. Третий цикл невозможен.

### 6.4 Trumpet-механика забора возвратов

Применима к **своим** заказам (для партнёрских отключена — партнёр сам
себе хозяин).

**В shipper-PWA в разделе «Возвраты»** — большая кнопка **«📢 Протрубить
возвраты»**. Один отправщик жмёт = на весь магазин.

- **Лимит 1 раз/день** на весь магазин. Если уже нажато — кнопка серая
  «Использовано на сегодня».
- При нажатии: для всех заказов в `return` создаются записи в
  `return_pickup_attempts` на сегодня (`result=NULL`).
- BullMQ-job `trumpet-notify` шлёт каждому клиенту с заказом в `return`
  DM «отправщик едет за возвратом, обновите код возврата». Расписание —
  «мини-история», а не спам (memory `trumpet_notify_design`): **#1 сразу
  → #2 +30 мин → #3 +1 ч → #4 +2 ч → #5+ каждые 3 ч**, окно **10:00–21:00
  МСК**. Job останавливается, как только клиент обновил код по всем своим
  возвратам (или trumpet-сессия отменена).
- Один DM на клиента с перечислением всех его заказов.
- Кнопка **«Отменить»** trumpet — любой отправщик. Удаляет попытки за
  сегодня, рассылает «ложная тревога», заказы остаются в `return`.
- После 21:00 МСК нажатие создаёт сессию и попытки (засчитывается),
  но уведомления не уходят (вне окна).

**На ПВЗ отправщик** на каждом возврате жмёт результат:

- ✅ **Забран** → `return_done`. Баланс клиента пополняется (см. 9.2).
- ❌ **Неверный код** → `result='wrong_code'`, заказ остаётся в `return`.
  Клиент получит DM «обновите код».
- ❌ **Неверный трек** → `result='wrong_tracking'`. Клиент получит DM
  «обновите трек».
- ❌ **Нет на ПВЗ** → `result='not_found'`. Норма для возвратов которые
  ещё не доехали — попытка засчитывается, trumpet продолжает в
  следующий день.
- ⚠️ **Брак по вине клиента** («ненадлежащее качество») →
  `executeDisputeReturn`: отправщик прикладывает **3–5 фото** +
  описание (обяз.). Заказ → `return_done`, `fault_party='client'`,
  `fault_reason='bad_quality'`, `dispute_photos`/`dispute_reason`,
  товар на склад **НЕ** возвращается (брак нельзя перепродать).
  **Деньги клиенту НЕ возвращаются** — товар испорчен клиентом,
  оплата остаётся у владельца. Клиенту DM с фото + инструкция в
  Авито-поддержку. Финансово: деньги у владельца → заказ **идёт в
  выручку** (§6.7, §9.3). Владелец при желании может вернуть вручную
  (§9.7 #3).

Если отправщик нажал trumpet но физически не доехал — попытка остаётся
с `result=NULL` (формальная попытка без визита).

### 6.5 Истечение `pickup_by` (сгорание возврата)

**Механизм:** ежедневный sweep `sweepStuckPickupByDaily` в 00:03 МСК
(симметрично send_by sweep'у). Per-order BullMQ-будильник
`scheduleExpirePickupBy` удалён 2026-05-26 — один cron, две независимые
функции для двух дедлайнов. См. `src/lib/jobs/sweep-expired-orders.ts`.

Авто-trigger при сгорании:

1. Заказ → `trash`.
2. Определяется `fault_party` + `fault_reason` (для статистики и
   рейтинга, на финансы не влияет).
3. Деньги клиенту автоматически **не возвращаются**. Если владелец
   решит вернуть — кнопка в панели.
4. Клиенту в DM: «возврат №X в утиле, причина: {…}». Для партнёрских —
   отдельная ветка с контактом партнёра (возврат шёл к нему, обсуждать
   с ним). Для не-партнёрских — контакт `@support_username` для
   разбирательства, если клиент считает что вина не его.
5. Владельцу/директору в DM при `fault_party='platform'` (owner-source
   only): сумма к возврату клиенту + контакт клиента (директор
   приоритетнее, fallback на owner-bot). Партнёрские platform-fault не
   шлются — деньги у партнёра, эскалация его сторона.
6. В owner-panel `/owner/orders/[id]` — бейдж «🟠 Наша вина — верни
   клиенту N₽» или «⚪ Вина клиента» рядом со статусом для status=trash.
7. **`source_warehouse='partner'`-исключение (с 2026-05-26):** для
   партнёрских заказов с самоотгрузкой (`source_warehouse='partner'`,
   партнёр сам отгружает и сам забирает возврат) `fault_party` НЕ
   ставится (NULL) — мы не фиксируем попытки партнёра у его ПВЗ,
   поэтому считать «вину платформы» автоматом было бы заведомо ложно.
   Клиенту DM с контактом партнёра, `partnerRefund.partnerLabel`
   ветка; владельцу DM при platform-fault не уходит. Шкала §6.6
   применяется только к owner-source и партнёрским с
   `source_warehouse='owner'`.

### 6.6 Адаптивные пороги попыток (определение `fault`)

Окно = `pickup_by - дата_оформления_возврата` (в днях).

| Окно (дней) | Требуется попыток |
| ----------- | ----------------- |
| 9–14        | 3                 |
| 6–8         | 2                 |
| 3–5         | 1                 |
| 0–2         | 0 (`late_report`) |

**Алгоритм:**

1. Если окно ≤ 2 → `fault_party=client`, `fault_reason=late_report`.
2. Иначе считаем `attempts_count` из `return_pickup_attempts`.
3. Если меньше требуемого → `fault_party=platform`,
   `fault_reason=no_attempts`.
4. Иначе → `fault_party=client`, `fault_reason`:
   - есть попытка с `result IN ('wrong_code','wrong_tracking','not_found')`
     → `wrong_data`.
   - все попытки с `result IS NULL` → `no_response`.

### 6.7 Возврат денег при возврате

- При `return_done` **«Забран и в порядке»** (без брака) —
  `customer_balance` пополняется на `client_price`. Это основной момент
  авто-возврата денег.
- ⚠️ **Исключение — `return_done` + `fault_reason='bad_quality'`**
  (брак по вине клиента, §6.4): деньги клиенту **НЕ** возвращаются
  (товар испорчен клиентом, оплата остаётся у владельца). Триггер
  `auto_credit_customer_balance` это пропускает (гард по `bad_quality`,
  миграция `20260518000160`). Такой заказ **учитывается в выручке**
  владельца (§9.3) — деньги фактически у него (симметрично `trash`).
- При `cancelled` до отправки (если был оплачен) — баланс пополняется.
- При `send_by` сгорел (если был оплачен) — баланс пополняется.
- При `trash` (pickup_by сгорел) — деньги **не** возвращаются авто.
  Клиент может переоткрыть (1 раз) или владелец вернёт руками.

В **+ВАЙБ-сценарии** возврат заказа уменьшает долг (если он есть на
этом заказе через `customer_vibe_debt` view). Если +ВАЙБ-долг по этому
заказу уже погашен (есть `vibe_payments`) — пополняется баланс как у
обычного клиента.

## 7. +ВАЙБ-кредит

### 7.1 Включение и лимит

- На клиенте флаг `vibe_enabled`. Включает только владелец.
- **Дефолт лимита** — `business_settings.vibe_credit_default_limit`.
- **Индивидуальное переопределение** — `customers.vibe_credit_limit_override`.
- Лимит = максимальный незакрытый долг. Сумма всех заказов с
  `is_paid=false` не может превышать его.
- **+ВАЙБ по умолчанию `false`** для нового клиента (само-вход через
  `/start`). Включается вручную владельцем по доверию.

### 7.2 Заказ в +ВАЙБ-режиме

Клиент в шаге 6 wizard-а видит кнопку «Оплатить позже (+ВАЙБ)».
Нажимает → заказ создаётся в `paid` с `is_paid=false`. Долг увеличивается
на `client_price`.

**Fallback на обычную оплату при превышении лимита** (с 2026-05-06):
если `currentDebt + price > limit` — wizard customer-bot и partner-bot
**не создают долговый заказ**, вместо этого предлагают обычную оплату.
В нормальном flow это поглощает кейс «лимит превышен», поэтому
авто-заморозка `auto_limit_exceeded` фактически срабатывает только
defensive backstop'ом (если кто-то опустил лимит вручную ниже долга).

Триггер `check_vibe_credit_freeze` — после INSERT/UPDATE заказа,
INSERT в `vibe_payments`, смены статуса в `return_done`/`cancelled`.

### 7.3 Заморозка / разморозка

**Типы заморозки** (с 2026-05-06):

- **`auto_limit_exceeded`** — defensive backstop, см. 7.2.
- **`vibe_revoked_with_debt`** — admin снял `vibe_enabled` при долге > 0.
- **`manual`** — владелец из `/owner/clients/[id]` нажал «Заморозить» с
  `required_payment_amount`. Фиксируется `frozen_debt_snapshot` в
  момент заморозки.

В боте у замороженного клиента остаётся **только** «💳 Оплатить долг».
Заказы не доступны.

**Авто-разморозка** (триггер `check_vibe_credit_freeze v3`):

- `auto_limit_exceeded` → когда долг ≤ лимит.
- `vibe_revoked_with_debt` → когда долг ≤ 0.
- `manual` → когда `(snapshot − current_debt) ≥ required_payment_amount`
  ИЛИ `current_debt ≤ 0`.

**Ручная разморозка** (с 2026-05-06): кнопка в `/owner/clients/[id]`
снимает `is_frozen` без погашения долга. Используется когда владелец
по доверию хочет вернуть клиента в работу.

Уведомление клиенту через `notifyCustomerVibeUnfrozen`.

### 7.4 Wizard оплаты долга (multi-select, с 2026-05-06)

1. Клиент жмёт «💳 Оплатить долг».
2. Бот группирует заказы по адресатам:
   - 🏠 «{business_name}» — долги перед владельцем.
   - Каждый партнёр — отдельная группа.
3. В выбранной группе бот показывает чекбоксы по заказам — клиент
   тапает нужные («toggle»). Сумма выбранных пересчитывается.
4. Кнопка «✅ Оплатить выбранные»:
   - **Owner-группа** → реквизиты владельца → клиент шлёт чек →
     Vision auto-confirm (см. §8). Если сумма ≥
     `business_settings.vibe_manual_threshold` (дефолт 50 000 ₽) —
     чек уходит **владельцу на ручное подтверждение**.
   - **Partner-группа** → реквизиты партнёра → клиент шлёт чек →
     чек пересылается партнёру. Vision не используется. Канон
     подтверждения (с 2026-05-12):
     - если в чеке **один заказ** — партнёр отвечает текстом
       «<номер> да» / «<номер> нет» (как при обычной партнёрской
       оплате), inline-кнопки не показываются;
     - если **несколько** — inline-кнопки «✅ Получил деньги» /
       «❌ Не пришли» (один тап закрывает всю группу).
5. После подтверждения создаётся `vibe_payments` + `vibe_payment_orders`
   (M2M на выбранные заказы). Триггер пересчитывает долг и при наличии
   партнёрских — обновляет `partner_owner_debts` (комиссия владельцу).
6. При снижении долга ≤ лимит → авто-разморозка (для
   `auto_limit_exceeded`) или см. правила 7.3 (для `manual`/`vibe_revoked`).

## 8. Vision auto-confirm чека

### 8.1 Четыре проверки (с 2026-05-02, применяются последовательно)

1. **Anti-replay:** `vision.operation_id` уникален в едином namespace
   `orders.vision_operation_id` + `vibe_payments.operation_id`. Если ID
   уже привязан к чеку — отклонение «чек уже использован» (заказ-flow
   проверяет оба реестра; +ВАЙБ-flow — тоже). На повторной попытке в
   той же сессии (заказ-flow) — эскалация директору (он видит шапку,
   новый чек, оригинал использования, инструкцию).

   **+ВАЙБ-погашение (с 2026-05-19, реализовано).** `recognize-receipt`
   до создания платежа проверяет `operation_id` против обоих реестров.
   При повторе: vibe_payment **не создаётся**, `is_paid` не трогается
   (как заказ-flow не создаёт заказ на replay), клиенту — терминальный
   отказ, владельцу — security-алерт (`vibe_replay`), факт в
   `activity_log`. Страховка на уровне БД: partial-UNIQUE
   `vibe_payments(operation_id) WHERE NOT NULL` (повторный insert →
   23505 → job падает, без двойного погашения). **Остаток:** если
   Vision не извлёк `operation_id` (или партнёрский маршрут без Vision)
   — `operation_id=NULL`, replay-защиты по нему нет (как и до 19.05);
   ужесточение до «нет operation_id → ручная проверка» — будущее
   решение (может блокировать легитимные платежи).

2. **Сумма:** `vision.amount >= ожидаемая_сумма − 1₽` (допуск копейка).
3. **Дата:** `vision.datetime >= momento_показа_реквизитов − 60 сек`.
4. **Получатель — жёсткий матчинг по типу платежа:**
   - `card` → совпадение last4 номера карты.
   - `sbp` → нормализованный 11-цифровый телефон.
   - `ip_qr` → имя ИП lowercase без префикса.

   Имя держателя НЕ участвует. Параметры `payment_methods.tier` см. §8.7.

### 8.2 Опорная точка даты

Момент когда бот в текущей wizard-сессии показал клиенту реквизиты.
Чек оплаченный раньше — заведомо не по этому заказу. Люфт 60 сек
покрывает округление времени банками.

### 8.3 Переплата (с 2026-05-02, потолок 300₽)

- `сумма_чека > ожидаемая` до **300₽** → auto-confirm. Переплата
  гасит долг FIFO через `apply_overpayment_atomic` (сначала +ВАЙБ-FIFO,
  остаток на `customer_balance`).
- Переплата > 300₽ → эскалация директору (вероятно ошибка клиента).

### 8.4 Эскалация директору / владельцу

С 2026-05-01 цепочка эскалации:

1. **Директор** (если привязан в `business_settings.director_tg_user_id`
   и роутинг `receipt_review='director'`) — получает чек, текстом
   подтверждает «N да» / «N нет» (где N — `pending_orders.order_number`).
2. **Владелец** — fallback если директор не привязан, либо если
   роутинг настроен на `owner`.

Триггеры эскалации:

- Vision не извлёк данные / не прошла одна из 4 проверок.
- Anti-replay при повторной попытке.
- Сумма ≥ `vibe_manual_threshold` (для +ВАЙБ-погашений).
- Переплата > 300₽.

`partner-receipts-digest` / `director-receipts-digest` шлёт сводку
каждые 3ч в окне (`director_notify_window_*` / `partner_notify_window_*`).

### 8.5 Применение баланса при оформлении (с 2026-05-01)

`create_pending_order_atomic` автоматически вычитает
`min(customer_balance, client_price)` → `pending_orders.applied_balance`.

- Если баланс **полностью покрыл** стоимость (`fully_paid_by_balance=true`)
  — wizard сразу зовёт `confirm_pending_order_atomic` без чека.
  Заказ с `payment_method='balance'`.
- При `cancel_pending_order_atomic` или TTL — баланс возвращается.

### 8.6 Sweep'ы для зависших pending'ов

- `sweepStuckVibeDebtPartnerPendings` — для +ВАЙБ-партнёрских pending'ов.
- `sweepStuckPartnerWarehousePendings` — для не-+ВАЙБ партнёрских с
  `receipt_received_at` без подтверждения.

Auto-cancel + DM клиенту/партнёру + escalation владельцу.

### 8.7 Ступенчатая ротация платёжных методов

`payment_methods.tier` (1=основные / 2=запасные / 3=резерв) +
`monthly_limit`. RPC `next_payment_method(amount)` сортирует:

1. `tier ASC` — нижние ступени включаются только когда верхние
   исчерпали лимит.
2. `(amount_used / monthly_limit) ASC` — pro-rata распределение
   внутри ступени.
3. `id ASC` — детерминированный tiebreaker.

UI: 3 кнопки выбора ступеней в `/owner/payment-methods`.

## 9. Финансовая модель

### 9.1 Принципы

- **Все переводы денег ручные.** ЮKassa / Split / автосписания не
  используются. Система фиксирует факты, не двигает деньги.
- **Возвраты оформляются через `customer_balance`** — накопительный
  баланс «сколько владелец должен клиенту». Клиент сам решает когда
  вывести.
- **Партнёрские деньги идут мимо нас.** Клиент платит партнёру
  напрямую. Партнёр копит долг по комиссиям перед владельцем.

### 9.2 Customer_balance — баланс клиента

**Архитектурная защита (с 2026-05-08):** все UPDATE баланса только
через RPC. TypeScript-код может только читать. История пишется только
из SQL-функций. Триггер `auto_credit_customer_balance` идемпотентен
(EXISTS-check по `(order_id, reason)`).

**Пополняется автоматически при:**

- `return_done` — отправщик/партнёр принял возврат, **если заказ был
  оплачен** (либо чеком, либо +ВАЙБ-долг по нему уже погашен). Сумма
  = `client_price`. Skip для `partner_id IS NOT NULL` (партнёр сам
  возвращает деньги, см. §10.3).
- `cancelled` до отправки — если был оплачен. Сумма = `client_price`.
- `send_by` сгорел — если был оплачен. Сумма = `client_price`.
- Ручное решение владельца «вернуть N₽ клиенту» (кнопка в панели).

**НЕ пополняется при:**

- Возврат +ВАЙБ-заказа с непогашенным долгом → уменьшается долг через
  `customer_vibe_debt` view. Без баланса.
- `trash` (`pickup_by` сгорел) → деньги остаются у владельца. Если
  владелец решит вернуть — через ручную кнопку.
- Возврат партнёрского заказа — партнёр сам возвращает клиенту вне
  системы (см. §10.3).

**Применение баланса при оформлении** (с 2026-05-01) —
`pending_orders.applied_balance` автоматически вычитается, при
cancel/expire возвращается. См. §8.5.

**Вывод денег клиентом** (рефактор 2026-05-08):

1. В профиле бота если `customer_balance > 0` — кнопка «Запросить вывод».
2. RPC `request_withdrawal_atomic` атомарно: INSERT request + DEC
   balance + INSERT history (`reason='withdrawal_request'`).
   Баланс **резервируется в момент создания запроса** — approve уже
   не двигает.
3. Каждый запрос получает уникальный `withdrawal_number` (отдельный
   sequence) для текстового подтверждения «N да / N нет».
4. `withdrawal-requests-digest` (cron каждые 3ч в окне
   `director_notify_window_*`) шлёт владельцу сводку pending'ов.
5. Владелец после перевода клиенту в DM owner-bot шлёт «42 да» —
   парсер вызывает `approve_withdrawal_request v3` (помечает done).
   «42 нет» → `reject_withdrawal_atomic` (возвращает баланс,
   `reason='withdrawal_rejected'`).
6. Клиент в любой момент может отменить через кнопку «❌ Отменить
   запрос вывода» → `cancel_withdrawal_atomic` (возвращает баланс,
   `reason='withdrawal_cancel'`).

**История движений** — таблица `customer_balance_history` (timestamp,
дельта, причина, привязка к заказу или ручной операции).

#### 9.2.1 Audit-view целостности (с 2026-05-08)

`customer_balance_integrity_view` проверяет инвариант:
`customers.customer_balance == SUM(customer_balance_history.delta)` для
каждого клиента. Если view возвращает строки — есть drift, нужна
диагностика. На проде drift = 0 у всех клиентов.

### 9.3 Выручка владельца

```
isRevenueCounted(order):
  включает:  paid, collecting, sent, return, trash, problem
  исключает: cancelled, return_done
  ИСКЛЮЧЕНИЕ: return_done + fault_reason='bad_quality' → ВКЛЮЧАЕТСЯ
              (брак по вине клиента, деньги у владельца — §6.4/§6.7,
               симметрично trash)
```

Правило одно: «учитываем, если деньги фактически у владельца».
Поэтому `trash` и `return_done(bad_quality)` — в выручке (деньги не
возвращены), а обычный `return_done`/`cancelled` — нет (возвращены).
(`reception_fault` как отдельная сущность в коде не существует —
бывший план, заменён на `fault_reason`; из канона убран.)

### 9.4 Прибыль владельца

> Авито-формула с `avito_fee_snapshot` + `avito_marketing_snapshot` — см. §15.5.

**Свой заказ:**

```
revenue_owner = client_price − purchase_price − shipper_rate_snapshot
```

**Партнёрский заказ:**

```
revenue_owner = partner_commission_snapshot
```

Деньги клиента идут партнёру напрямую — у владельца в выручке только
комиссия. `purchase_price` и `shipper_rate` в партнёрском не участвуют.

> **Статус реализации (2026-05-18, ЧАСТЬ C ЗАКРЫТА).** Все 4 экрана
> (страница товара, Аналитика, Финансы, Дашборд) считают выручку/
> себестоимость/прибыль одним хелпером `lib/finance/owner-revenue.ts`.
> Реализовано полностью: §9.3 (гейт `isRevenueCounted`, в т.ч. кейс
> `return_done(bad_quality)` в выручке) + партнёрский =
> `partner_commission_snapshot` + **вычет
> ставки отправщика**: `ownerCost(свой) = purchase_price +
shipper_rate_snapshot`. `orders.shipper_rate_snapshot` заполняется
> БД-триггером `orders_snapshot_shipper_rate` при переходе в `sent`
> (ставка «на сейчас» по режиму выплат — §9.5; helper
> `shipper_current_rate`). При откате из `sent` снимок снимается.
> Для исторических заказов, отгруженных ДО 2026-05-18, snapshot = NULL
> → их себестоимость = только закупка (ставка не ретро-применяется).
>
> **Нюанс pendulum.** Снимок — ставка НА МОМЕНТ отгрузки (по текущему
> `shipper_score`). Точный дневной заработок отправщика досчитывается
> ELO-джобой в 00:10 и живёт в `shipper_stats.earnings` (операционный
> реестр выплат). Прибыль §9.4 — аналитическая оценка по at-ship
> снимку; малое расхождение sum(snapshot) vs sum(earnings) допустимо
> и намеренно (разные назначения: аналитика прибыли vs реестр выплат).

### 9.5 KPI отправщиков

**Модель выплат — 2 режима на выбор владельца** (решение 2026-05-18,
реализовано; настройка `settings.shipper_payment_mode ∈
{'pendulum','fixed'}`, CHECK-инвариант; UI — карточка на
`/owner/shippers`):

- **`pendulum` (маятник, по рейтингу).** Живая ELO-система. У отправщика
  `users.shipper_score` 0–100 — постоянный рейтинг. Ежедневная джоба
  `update_shipper_scores` (00:10 МСК) двигает score от **доли
  отгруженных доступных заказов** за день: `expected = score/100`,
  `delta = K × (completion − expected)`, асимметрия ×2.5 (падать легче),
  K = 32 (стаж < 30 дн с отгрузками) иначе 16. **Доступно за день**
  (канон §4.2, бывший баг B1 с мёртвым `awaiting_shipment` исправлен) =
  заказы, отгруженные (`sent`) в этот день **плюс** открытые
  `paid/collecting/problem` на конец дня, делённые на число активных
  отправщиков (по `work_days`). Ставка за заказ =
  `rate_min + score/100 × (rate_max − rate_min)`. `shipper_stats.
earnings` за день = `orders_shipped × rate` (досчитывается в 00:10 с
  новым score).
- **`fixed` (фиксированная).** `shipper_fixed_rate` ₽ за каждый
  отгруженный (`sent`) заказ. `shipper_stats.earnings = orders_shipped
× fixed_rate`, `rate_applied = fixed_rate` (начисляется сразу в
  `increment_shipper_stat` при `sent` — бывший баг B3 «0₽» закрыт).
  `update_shipper_scores` в этом режиме рейтинг не трогает (score
  заморожен, показывается как информационный KPI).

`increment_shipper_stat` вызывается при `sent` (+1 `orders_shipped`),
`return_done` (+1 `returns_collected`, **без оплаты**) и откате
(`-1`). Возвраты заработок не дают (отдельная KPI-метрика). Helper
`shipper_current_rate(shipper)` отдаёт ставку «на сейчас» по режиму —
используется триггером снапшота `orders.shipper_rate_snapshot` (§9.4).

> Старый разнобой режимов (`dynamic`/`per_order` в коде, тарифная сетка
> `shipper_rate_tiers`, daily-goal-бонусы и streak-множители) — выпилен
> из модели как B2. Поля `shipper_penalty_rate` / `shipper_rate` /
> pendulum-extra (`rate_base`/`speed_target`/`avg_window`) /
> `payout_cadence` остались в БД, но в каноне/UI не участвуют — мёртвый
> конфиг, дочистка вынесена в финальную фазу полировки.

В карточке каждого отправщика две KPI-метрики (рейтинг — отдельно):

**1. «Доля возвратов забранных в срок»:**

```
rate = count(return_done у отправщика) /
       count(return_done + trash где fault_party='platform' AND
                                     fault_reason='no_attempts')
```

**2. «Доля незавершённых сборок»:**

```
rate = count(collecting→paid авто-откатов) /
       count(«Беру в работу» нажатий)
```

Обе считаются из `status_history` событий с фильтром по флагу
`is_auto_revert` (отличает авто-откаты от ручных операций).

> Метрика «доля неотгруженных после печати» убрана: печать стикера —
> опциональный флаг `barcode_printed`, не статус и не гейт (§4.2), а
> «взял в работу, но не сдал» уже покрывает метрика 2.

### 9.6 Выплата отправщику

**Ledger-модель ОТМЕНЕНА 2026-05-18.** Канон-журнал
(`shipper_ledger_entries` + `shipper_payout_periods` + период-выплаты
`build_shipper_payouts_for_period`/`mark_shipper_payout_paid`) был
мёртвым кодом: триггер срабатывал на статус `completed`, которого в
каноне нет (§4.2 — успешный терминал = `sent`), журнал никогда не
наполнялся. Таблицы/триггер/RPC/`/owner/payouts`/`build-shipper-payouts`
джоба удалены (миграция `20260518000150`).

**Новая модель — простой реестр факта выплат:**

- Накопленный заработок отправщика живёт в `shipper_stats.earnings`
  (см. §9.5, считается по режиму pendulum/fixed). Это **операционный
  реестр**: сколько отправщику начислено.
- «К выплате» = `Σ shipper_stats.earnings − Σ shipper_payouts.amount`
  (за период / всего). Показывается отправщику (Shipper PWA «Деньги»)
  и владельцу (карточка отправщика, страница отправщика).
- Владелец переводит деньги вне системы и **фиксирует факт** —
  `/owner/finance` → вкладка «Выплаты» → «+ Выплата» (POST
  `/api/owner/finance` type=`payout` → `INSERT shipper_payouts`).
  Жёсткого расписания/периодов нет (cadence-настройки выпилены).
- При фиксации отправщику уходит DM «✅ Выплата переведена»
  (`notifyShipperPayoutPaid`).
- `return_done`/`trash` заработок отправщика **не отзывают** (услуга
  доставки оказана — отправщик своё дело сделал; clawback'а нет).
- Безопасность: создание выплат / смена ставок — операции ТОЛЬКО
  владельца (§9.7). `/api/shipper/payouts` — read-only (POST/PATCH
  убраны 2026-05-18, клиент-обёртка `useCreatePayout` удалена).

### 9.7 7 ручных операций владельца

1. Подтвердить крупное +ВАЙБ-погашение (≥ `vibe_manual_threshold`).
2. Списать N₽ с баланса клиента (после фактического перевода).
3. Создать произвольный возврат денег клиенту (кнопка «Вернуть N₽
   клиенту» на любом заказе → пополнение `customer_balance`).
4. Принять выплату от партнёра по комиссиям (партнёр прислал чек
   погашения долга в partner-bot).
5. Зафиксировать факт выплаты отправщику (перевёл вне системы →
   `/owner/finance` «+ Выплата» → `shipper_payouts`; §9.6, без периодов).
6. Заморозить / разморозить клиента вручную.
7. Установить +ВАЙБ-флаг и индивидуальный лимит на клиенте.

Всё остальное — автомат.

### 9.8 Касса — обязательства владельца (защита от кассового разрыва)

Реализовано 2026-05-18. Владельцу нужен «реальный кэш» = деньги на
картах − обязательства. Две величины:

- **Должен клиентам (баланс)** = `Σ customers.customer_balance` (>0).
  Возвраты/ручные начисления (§9.2). Клиент может вывести в любой
  момент — владелец обязан держать эту сумму на картах **нетронутой**.
- **Клиенты должны (+ВАЙБ)** = `Σ customer_vibe_debt.debt` (§7.4).
  Заказы в долг. Этих денег на картах **ещё нет** — виртуальное
  ожидаемое поступление, не «свободный кэш».
- **Партнёры должны (комиссии)** = §10.4 канон-формула
  (`status='sent'` + `partner_payment_received_at` + НЕ
  `partner_commission_paid_at`), `Σ partner_commission_snapshot`
  (с 2026-05-19). Тоже ожидаемое поступление, не текущий кэш.
  **Read-only зеркало** того же расчёта, что на `/owner/partners` —
  таблица `partner_owner_debts` здесь НЕ участвует (дуал-реестр —
  открытое решение, профильный проход Партнёры).

«Реальный свободный кэш» = деньги на картах − «Должен клиентам».
+ВАЙБ-долг и партнёрский долг показываются отдельно как ожидания (не
вычитаются, не прибавляются к кэшу).

**Где показано (решение по размещению — Claude, автономно):** Касса —
**глобальная** казначейская величина, не привязана к товару/периоду.
Поэтому:

- **Аналитика** (`/owner/analytics`) — **главная точка** обзора
  финансов. KPI (Прибыль/Выручка/Вложено/ROI/Ср.чек + дельты —
  `FinancialHero`), интерактивный график `TrendChart` (5 метрик +
  comparison vs прошлый период), DayHeatmap, OrderFunnel, ProductMatrix
  (с ABC/недостача/оборот), ClientAnalytics, HealthScore + Forecast.
  **Карточка-мост `FinanceSummaryCard`** (с 2026-05-20, между
  `TrendChart` и `DayHeatmap`, owner-only) — Apple-стиль summary →
  drill-down: 2 hero-числа (Чистая прибыль за период + Касса/
  обязательства) + утилитарная строка (Расходы и Выплаты с
  кол-вом записей); вся карточка кликабельна → `/owner/finance`.
  API `/api/owner/analytics` отдаёт `financeSummary` (`netProfit`,
  `totalExpenses`/`expensesCount`, `totalPayouts`/`payoutsCount`,
  `treasury`: `customerBalanceOwed` + `vibeDebtTotal` +
  `partnerDebtOwed`) — те же канон-формулы §9.4/§9.8/§10.4 что и
  на /api/owner/finance.
- **Финансы** (`/owner/finance`) — **операционная страница**
  (журналы и Касса). Slim-сводка наверху (4 цифры: Чистая прибыль /
  Касса / Расходы / Выплаты — те же, что на карточке-мосту), затем
  3 вкладки: **Расходы** (журнал + добавить + категории), **Выплаты**
  (журнал выплат отправщикам + добавить), **Касса** (3 карточки
  обязательств + список +ВАЙБ-должников). Ссылка «↗ Сводка и графики
  — на Аналитике» в шапке. **Удалено в 2026-05-20:** KPI (5 карточек),
  Donut, блок «Динамика» (SalesChart), вкладка «Товары» — переехали на
  Аналитику (ProductMatrix там богаче, чем бывший Финансы-Товары).
- **Дашборд** — компактная карточка-зеркало (2 цифры + ссылка в
  Финансы). `dashboard` сервис → `treasury`.
- **НЕ** на странице товара: там данные scoped по
  товару/периоду, а Касса — общая по всем клиентам на «сейчас».
  Вклеивать туда глобальную сумму = вводить в заблуждение (был соблазн
  по тексту запроса; осознанно НЕ делаем, фиксируем здесь).

`customer_balance_integrity_view` (§9.2.1) остаётся audit-инвариантом
для ручной сверки в SQL Studio (drift = 0 в проде).

## 10. Партнёрский поток

### 10.1 Регистрация партнёра

1. Владелец в панели создаёт запись в `partners` (`name`,
   `tg_username`). Запись создаётся с `is_active=false` — партнёр
   ещё не настроил реквизиты, его товары пока не показываются клиентам.
2. Система генерирует `invite_token`. Владелец отправляет ссылку
   `t.me/{partner_bot}?start=<token>`.
3. Партнёр жмёт ссылку → `tg_user_id` привязывается к `partners`.
   Бот предупреждает: «Сначала настрой реквизиты через ⚙️ Мои
   реквизиты — пока их нет, твои товары не появятся в каталоге».
4. Партнёр через **⚙️ Мои реквизиты** настраивает статичные реквизиты
   (текст: карта/СБП/ИП — или фото с QR-кодом). После двушагового
   подтверждения («Сохранить такие реквизиты? ✅/✏️») запись пишется
   в `partners.payment_requisites` (jsonb с типами `text`/`photo`),
   и `is_active` ставится в `true`.

### 10.2 Денежный поток по складам (с 2026-05-05)

Склад партнёра (`products.partner_stock_location` — длинные значения
`partner_warehouse`/`owner_warehouse`) влияет **ТОЛЬКО на отгрузку**, не
на платёжный flow. Все партнёрские заказы — деньги партнёру напрямую,
независимо от того где физически лежит товар.

При создании заказа `products.partner_stock_location` маппится в
короткий снэпшот `orders.source_warehouse` (`CHECK ('owner','partner')`):

| `source_kind` | `source_warehouse` | Откуда (`partner_stock_location`) | Кто получает оплату | Vision | Кто отгружает       |
| ------------- | ------------------ | --------------------------------- | ------------------- | ------ | ------------------- |
| `owner`       | `owner`            | —                                 | владелец            | ✅     | отправщик владельца |
| `partner`     | `partner`          | `partner_warehouse`               | **партнёр**         | ❌     | партнёр сам         |
| `partner`     | `owner`            | `owner_warehouse`                 | **партнёр**         | ❌     | отправщик владельца |

**Реквизиты — статичные.** Партнёр настраивает их один раз через
`⚙️ Мои реквизиты` (см. 10.1 п. 4). Клиент при оформлении партнёрского
заказа сразу получает эти реквизиты, без ожидания партнёра.

### 10.2.1 Жизненный цикл партнёрского заказа (с 2026-05-26)

1. Клиент в wizard'е заказа выбирает партнёрский товар. Товары
   партнёров без реквизитов или `is_active=false` фильтруются из
   каталога.
2. На шаге «Оформить» создаётся `pending_orders.row` (для не-+ВАЙБ —
   pending, см. §4.1) или сразу `orders` (для +ВАЙБ).
3. customer-bot сразу шлёт клиенту реквизиты партнёра:
   - `payment_requisites.type='card'/'sbp'` → текст в `<code>`;
   - `payment_requisites.type='ip_qr'` → фото с QR-кодом.
4. BullMQ-job `expire-pending-order` (10 мин) или
   `partner-payment-expire` (24ч после получения чека) — авто-отмена.
5. Клиент платит партнёру напрямую и шлёт фото чека в customer-bot.
6. customer-bot форвардит чек партнёру в DM partner-bot с карточкой
   заказа. Партнёр текстом «N да» / «N нет» подтверждает (где N —
   `order_number`). Кнопок нет — защита от случайного тапа.
   **Канон 2026-05-12:** единичный заказ — всегда текстом; группа
   из нескольких (только в +ВАЙБ multi-select wizard, см. §7.4) —
   inline-кнопками. Та же модель у director/owner.
7. Партнёр пишет:
   - **`N да`** → `confirm_pending_order_atomic` → заказ в `orders` со
     `is_paid=true`. Клиенту: «✅ Заказ №N — оплата подтверждена».
   - **`N нет`** → pending отменяется (`cancel_pending_order_atomic`),
     клиенту DM «оплата не пришла, обсуди с партнёром в ЛС».
     **Канон 2026-05-26:** на этом шаге только бинарка — без выбора
     причины. Сценарии «нет товара / нет размера» переехали в
     карточку 🚚 «На отправку» (после confirm-чека), потому что
     физическое наличие проверяется в момент сборки, а не получения денег.
8. Если партнёр молчит 24ч в окне `partner_notify_window_*` →
   auto-cancel + эскалация в `support_telegram_username` (директор).
9. Для партнёрских с `source_warehouse='owner'` — отгрузку делает
   отправщик владельца через shipper PWA. Для
   `source_warehouse='partner'` — партнёр сам через карточку заказа в
   partner-bot (см. §10.2.2).

### 10.2.2 «📦 Мои заказы» у партнёра (с 2026-05-26)

Партнёр в DM партнёр-бота имеет раздел «📦 Мои заказы» — список всех
своих заказов с фильтрами (Активные / Завершённые / Отменённые / Все),
кликабельные карточки + контекстные действия. Индикатор статуса
учитывает `orders.source_warehouse` (короткий снэпшот `'owner'`/`'partner'`):

| Статус заказа          | `source_warehouse='partner'` | `source_warehouse='owner'`      |
| ---------------------- | ---------------------------- | ------------------------------- |
| `paid`/`collecting`    | 🚚 «На отправку»             | 📦 «У владельца» (info)         |
| `return`               | ⚠️ «Забрать возврат»         | 📦 «Возврат у владельца» (info) |
| `sent` / `return_done` | ✅                           | ✅                              |
| `cancelled` / `trash`  | ❌                           | ❌                              |

**Кнопки на карточке (только `source_warehouse='partner'`):**

- 🚚 → **«✅ Отправил»** (`paid → sent`), **«❌ Нет размера»**,
  **«❌ Нет товара»**.
  Трек партнёр не вводит — он уже есть в заказе (клиент прислал в
  оформлении). При «нет размера/товара» заказ моментально → `cancelled`
  с reason `partner_size_out`/`partner_product_out`, клиенту DM
  «партнёр не может отправить, возврат денег обсуди с ним напрямую»
  - контакт, партнёру DM «верни клиенту X₽». Сток у этого партнёра:
    `current_quantity=0` для размера или `is_in_stock=false` для товара.
- ⚠️ → **«✅ Забрал»** (`return → return_done`). Дальше — переписка
  с клиентом в ЛС, остальные исходы (неверный код/трек, нет на ПВЗ)
  не имеют кнопок: партнёр обсуждает с клиентом напрямую.
- 📦 — info-only, кнопок нет.

**Список дел партнёра (digest).** Существующий `partner-receipts-digest`
расширен: одно DM раз в `partner_digest_step_hours` (по умолчанию 3ч)
в окне `partner_notify_window_*` со всеми типами дел:
💳 «Чеки на проверке», 🚚 «На отправку», ⚠️ «Забрать возврат».
Если все секции пусты — DM не уходит.

### 10.3 Возврат партнёрского заказа (с 2026-05-26)

- Клиент в customer-bot оформляет возврат (трек + `pickup_by`, без
  кода — партнёр договаривается с клиентом лично).
- partner-bot шлёт партнёру DM: «Клиент @{tg_username} оформил возврат
  №X. Заберите до DD.MM. Код возврата клиент пришлёт лично, пиши ему».
- **`source_warehouse='owner'`:** возврат идёт на наш ПВЗ, забирает
  наш shipper через PWA (та же логика что для собственного заказа,
  §6.4). Партнёр видит заказ как 📦 (info-only).
- **`source_warehouse='partner'`:** партнёр сам забирает со своего ПВЗ
  через карточку «📦 Мои заказы» → **«✅ Забрал»**
  (`return → return_done`).
- **При ✅ Забран → `return_done`:**
  - `customer_balance` НЕ пополняется (триггер
    `auto_credit_customer_balance` skip для `partner_id IS NOT NULL`).
  - Партнёру шлётся `notifyPartnerOrderRefundDue(kind='return_done')`
    — DM с контактом клиента и поддержки.
  - Клиенту в `notifyCustomerOrderReturnPickedUp` — текст с контактом
    партнёра и поддержки (вместо «N₽ зачислено на баланс»).
  - Партнёр вне системы возвращает деньги клиенту. Факт обмена денег
    в нашей БД не фиксируется — это **зона партнёра ↔ клиента**, не
    наша.
- При истечении `pickup_by` → `trash`. См. §6.5: для
  `source_warehouse='partner'` ярлык «вины» НЕ ставится (партнёр сам
  отгружает, мы не фиксируем его попытки забора), для
  `source_warehouse='owner'` — обычная шкала §6.6.
- При cancel партнёрского заказа — аналогичный DM
  `notifyPartnerOrderRefundDue(kind='cancelled')`.
- **Trumpet-механика для партнёрских** реализована (с 2026-05-08) —
  кнопка «📢 Протрубить возвраты» в partner-bot, серия DM-job'ов
  клиентам в окне `trumpet_notify_window_*`. См. §6.4.

### 10.4 Партнёрский долг по комиссиям

- При `sent` — на партнёре активируется обязательство «выплатить
  владельцу `partner_commission_snapshot`». **Только `sent`:** если
  партнёрский заказ ушёл в `return`/`return_done`/`cancelled`/`trash`,
  обязательство по комиссии НЕ возникает/снимается (партнёр сам вернул
  деньги клиенту, §10.3). owner-панель и partner-bot считают долг
  одинаково — по заказам в `status='sent'` с
  `partner_payment_received_at` и без `partner_commission_paid_at`
  (фикс 2026-05-19: панель раньше не фильтровала статус → завышала).
- Партнёр копит долг. В owner-панели на карточке партнёра —
  «висит N₽ долга по комиссиям» + список формирующих заказов.
- **Каноническая модель (с 2026-05-26):** `orders.partner_commission_paid_at`
  - фильтр `status='sent'` — единственный источник истины. Закрытие —

    батчем). `owner-panel`, `partner-bot` и `/owner/finance` все читают
    одну и ту же агрегацию из `orders`.
- **Таблица `partner_owner_debts` оставлена только для прочих долгов** —
  ручные корректировки владельца + исторические compensation-записи
  (`reason IN ('size_out_money_received', 'product_out_money_received')`

  Запись с `reason='partner_commission'` в таблицу **больше не пишется**:
  - `confirm_pending_order_atomic` v18 (миграция `20260526000052`) —
    INSERT удалён.
  - `trg_partner_debt_on_vibe_payment` триггер + функция снесены
    (миграции `20260526000050/000051`).
  - `cancel_pending_order_atomic` v5 (миграция `20260526000053`) —

- partner-bot:
  - Кнопка «💳 Долг по комиссиям» — детализация заказов, кнопка

  комиссии списываются с долга, заказы получают

- **Лимит долга партнёра не автоматизирован.** Владелец вручную ставит

### 10.5 Денежный поток

- Клиент платит **партнёру напрямую** на per-order реквизиты
  (см. 10.2).
- Партнёр копит долг по комиссиям перед владельцем (см. 10.4).
- При возврате — партнёр возвращает деньги клиенту (см. 10.3).

В выручке владельца отражается только `partner_commission_snapshot`
(см. 9.4).

## 11. Статус `problem` — две отдельные ветки

`problem_type` в БД — `out_of_stock` (расхождение склада) или
`bad_barcode` (трек, который прислал клиент, не сканируется на ПВЗ при
отправке). Это **разные процессы** — обработка, уведомления и
возобновление различаются.

### 11.1 Ветка `out_of_stock` — расхождение склада

> Для Авито-заказов выборка кандидатов расширяется на
> `status IN ('return', 'return_in_transit')` с условием
> `expected_return_date <= send_by − 1 день` — см. §15.6.

#### Триггер

Отправщик в `paid` / `collecting` физически не находит товар или размер,
хотя в БД остаток есть. Жмёт **«Проблема» → «Нет товара»** → модалка с
выбором scope (для одиночного заказа — две кнопки, для batch — одна
дефолтная `single`):

- **«Только на этот заказ»** (`scope='single'`) — отправщик не нашёл
  одну единицу, но допускает что для других активных заказов того же
  размера товар может оказаться.
- **«На все заказы по этому размеру»** (`scope='all'`) — отправщик
  уверен что физически нет ни одной единицы. Каскад: все остальные
  активные `paid`/`collecting` заказы того же `product_size_id` идут
  через ту же логику problem+linked / cancel.

В **обоих** режимах:

- `current_quantity` обнуляется на 0 — размер моментально снимается с
  продажи (новых заказов оформить нельзя пока товар не появится).
- Применяется логика «привязка возврата или моментальная отмена»
  (см. ниже).

> История: до 2026-05-26 каскад был **жёстким** — БД-триггер
> `cascade_problem_orders` каскадил все заказы безусловно. Триггер
> убран, логика переехала в код (`executeMarkProblem` в
> `src/lib/orders/shipper-actions.ts`).

#### Привязка к возврату или моментальная отмена

Для каждого problem-заказа (основной + каскадные при `scope='all'`)
система ищет подходящий возврат того же `product_size_id` в порядке
FIFO по `send_by` (самым горящим возвраты достаются первыми):

- Статус возврата = `return`.
- **Эффективная дата прибытия** ≤ `send_by` заказа (иначе возврат
  придёт после дедлайна и не спасёт).
  - Авито-возврат — `expected_return_date` из API.
  - Дроп-возврат — `expected_return_date` обычно NULL → клиент уже
    отметил «приехал на ПВЗ» (см. §6.4) → считаем «уже на ПВЗ сегодня».
- Не привязан к другой проблеме (`linked_return_order_id` уникален).
- **Partner-isolation (с 2026-05-26):** `partner_id` возврата должен
  совпадать с `partner_id` проблемного заказа (NULL ↔ NULL для
  owner-source, X ↔ X для конкретного партнёра). De-facto это
  гарантировано через `product_size_id` (один товар = один источник),
  но явный guard в `fetchAvailableReturnsForSize` и cascade siblings
  защищает от будущих data-inconsistency. Каскад `scope='all'` также
  ограничен `partner_id`-match.

**Если возврат найден** — `linked_return_order_id` проставляется +
`system_comment` с подсказкой:

- «Возврат заказа №N уже на ПВЗ — забери для отправки» (если уже на ПВЗ).
- «Размер для отправки придёт с возврата заказа №N (ожидается DD.MM)»
  (если в пути).

**Если возврат не найден** — заказ моментально → `cancelled` с
`cancel_reason='out_of_stock_no_return'` + refund по канону §9.2:

- Owner-source оплаченный → `credit_customer_for_order` на баланс.
- Partner-source оплаченный → DM партнёру + клиенту с контактами
  (партнёр сам возвращает напрямую, см. §10).
- Неоплаченный (legacy / +ВАЙБ-долг) → освобождается резерв,
  кредитование баланса не нужно.

#### Возобновление

Размер становится доступен автоматически когда:

- Возврат принят (`executeCompleteReturn` → `return_done`) — триггерит
  job `auto-resume-problem`.
- Владелец поднял остаток в панели — **любой** путь: приход/сверка/
  поправка (`/stock`), партии add/edit (`/batches`), **редактор
  размеров** (`replace_product_sizes`, с 2026-05-19) — каждый шедулит
  job для размеров, ушедших с 0 на >0.

> **Механизм (для разработки):** триггер
> `notify_size_quantity_restored` шлёт `pg_notify('auto_resume_problem')`,
> но LISTEN-консьюмера НЕТ — канал мёртв (cosmetic-долг, фаза
> полировки). Реальный механизм — **явный вызов**
> `scheduleAutoResumeProblem(product_size_id)` из роутов после рестока.
> Хендлер сам no-op если problem-заказа нет; не перепроверяет остаток —
> поэтому вызывающий обязан звать только для размеров с qty > 0.

Job берёт **один** problem-заказ с минимальным `send_by` (FIFO),
переводит в **`paid`** (общий пул, с 2026-05-26 — раньше `collecting`),
сбрасывает `claimed_by`/`claimed_at`, очищает `problem_type` и
`linked_return_order_id`, переписывает `system_comment` на «Размер
взят с возврата заказа №N». Прежнему `claimed_by`-отправщику шлёт
DM с напоминанием — успей взять до сгорания. Любой свободный отправщик
видит заказ в табе «Собрать» и может взять через executeStartCollecting.

> **Policy-fork закрыт (с 2026-05-26):** выбран «общий пул» над
> «персональный resume» — устойчиво к недоступности конкретного
> shipper'а (offline / выходной), заказ не блокируется до сгорания
> `send_by`. Бывший `claimed_by` получает DM-напоминание, но не имеет
> приоритета — кто первый взял, тот и собирает.

Если до `send_by` товар так и не появился — заказ → `cancelled` через
job `expire-send-by`. Деньги возвращаются на customer_balance с reason
`send_by_expired` (см. §9.2).

#### UX в Shipper PWA

Заказы с `problem_type='out_of_stock'` **скрыты** из таба «Собрать» —
системе нечего показывать отправщику до auto-resume. После auto-resume
заказ всплывает в табе «В работе» (`collecting`) с system_comment-подсказкой.

#### Уведомление владельцу (out_of_stock)

owner-bot шлёт DM по route `order_problem` с метриками
(RPC `get_stock_mismatch_context`):

> ⚠️ **Расхождение склада**
> {product_name} · размер {L}
>
> По базе должно быть: **{current_quantity}** шт.
> Отправщик не нашёл при сборке заказа №{order_number}.
>
> **Возвраты на этот размер:**
> • {in_transit_count} в пути (ближайший — {nearest_expected_return})
> • {on_pvz_count} уже на ПВЗ
>
> Сейчас в проблеме: **{problem_count}** заказа(ов).
>
> → /owner/products/{product_id}

Если возвратов нет вообще — отдельная строка «Возвратов нет — заказ
дождётся `send_by` и сгорит».

#### Уведомление клиенту (out_of_stock)

> ⚠️ Заказ №X — нашли проблему.
> Размера сейчас нет в наличии — ищем замену из ближайшего возврата.
> Напишем, как только будет ясность.

Кнопок действий нет, кроме «Отменить заказ».

### 11.2 Ветка `bad_barcode` — трек не сканируется

#### Триггер

Отправщик пытается отправить заказ через ПВЗ → трек, который прислал
клиент при оформлении, не сканируется → жмёт **«Проблема» → «Трек не
сканируется на ПВЗ»** → заказ → `problem` с `problem_type='bad_barcode'`,
system_comment «Трек не сканируется на ПВЗ — ждём новый от клиента».

#### Уведомление клиенту (bad_barcode)

> ⚠️ Заказ №X
> Твой трек `{tracking}` не сканируется на ПВЗ при отправке.
> Зайди в «📦 Мои заказы» → этот заказ → «✏️ Обновить трек отправки» —
> пришли новый номер, и заказ автоматически вернётся в работу.

#### Уведомление владельцу

**НЕТ.** Это диалог отправщик ↔ клиент, владельцу делать нечего.

#### Возобновление

Клиент в своей карточке заказа (customer-bot, «📦 Мои заказы») жмёт
**«✏️ Обновить трек отправки»** → присылает новый трек одним
сообщением → одной транзакцией: `tracking_number` обновляется, статус
→ `paid`, `problem_type` и `claimed_by` сбрасываются (заказ
возвращается в общий пул, любой свободный отправщик может взять).
Защита: проверка на статус `problem`+`bad_barcode` в WHERE; проверка
что новый трек ≠ старому.

Резервный путь — отправщик в PWA жмёт **«Вернуть в работу»**
(`undo_problem`) → `paid` / `collecting`. Используется если клиент
обновил трек через @support / вне бота. Auto-resume для bad_barcode НЕ
работает (он только для `out_of_stock`).

#### UX в Shipper PWA

Заказы с `problem_type='bad_barcode'` **остаются видимыми** в табе
«Собрать» — это активная задача отправщика, ждёт его действия после
ответа клиента.

### 11.3 Avito vs дроп

В обеих ветках разная семантика возврата (см. §15 + AVITO_INTEGRATION_BRIEF):

- **Дроп-возврат**: `expected_return_date=NULL`, статус `return` =
  «клиент сам отметил, что возврат на ПВЗ» (одна кнопка в боте).
- **Авито-возврат** (фаза 3): `expected_return_date` из Авито-API,
  статус `return` означает «в пути или на ПВЗ» в зависимости от даты.

### 11.4 Учёт недостач склада (сверка инвентаризации, с 2026-05-16)

«Недостача» (пропавшие безвести единицы) считается **только по сверке
инвентаризации**, НЕ формулой `initial − продано − остаток` — формула
ненадёжна: возвраты/коррекции/партнёрские смещают её, а `initial`
накопительно растёт только на «Приход» (правки формы — `GREATEST`).
Точка истины — независимый физпересчёт (отправщик или владелец).

- **Источник — два пути сверки:** (1) отправщик в Shipper PWA
  `/shipper/stock` вводит факт; (2) владелец на странице товара жмёт
  **«Поправить остаток»** и выбирает «потеря/излишек». Оба пути при
  `факт ≠ current` пишут событие в **`stock_reconciliations`**
  (`system_before`, `counted`, `delta`, `purchase_price_snapshot`,
  `reconciled_by` = кто сверял) и **авто-сверяют `current := факт`**.
  Покрыты **и размерные товары, и One Size** — единообразно.
- **Атомарность.** Запись события + авто-сверка идут одной транзакцией
  через RPC `reconcile_product_stock` (метод проекта, ср.
  `replace_product_sizes` / `*_atomic`). Журнал недостач и фактический
  остаток не могут разойтись при обрыве на полпути.
- **delta** = `system_before − counted`: `>0` — недостача (система
  думала больше), `<0` — излишек (нашли больше: неучтённый возврат /
  прошлый недосчёт).
- **Два явных действия владельца над остатком размера** (страница
  товара; заменяют старое поле-угадайку):
  - **«Приход» (+N)** — пришла новая партия: `current += N` И
    `закуплено (initial / products.purchase_quantity) += N`. Это
    **единственное** действие, означающее «потрачены деньги»; на
    недостачу не влияет. RPC `restock_product_size`.
  - **«Поправить остаток» (=M)** — владелец вводит физфакт, система
    спрашивает про разницу: **потеря/излишек** → `reconcile_product_stock`
    (пишет событие, `current := M`); **поправка опечатки** →
    `correct_product_size_quantity` (`current := M`, «закуплено» НЕ
    трогаем, событие НЕ пишем). RPC.
    В форме редактирования товара количество существующих размеров —
    **только для чтения** (меняется этими двумя действиями); форма —
    только структура (добавить/переименовать/удалить размер).
- **НЕ пишется в недостачу:** «Поправка опечатки» владельца (тихая
  коррекция неверной цифры — не потеря); §11.1 «нет товара» (разовый
  инцидент). Потеря фиксируется, только когда отправщик при пересчёте
  или владелец через «Поправить остаток» **явно** её признал.
- **Где видно владельцу:** список «Товары» — фильтр **«С недостачей»**
  (сортировка по убыванию) + красный бейдж «−N» на карточке; страница
  товара — блок «Недостачи / сверки» (сумма −N шт · −X ₽ по закупочной-
  снимку, излишки отдельно, лента событий). Отдельной страницы нет
  (решение пользователя: не плодить страницы).
- ₽ потери = `delta × purchase_price_snapshot` (снимок закупочной на
  момент сверки).

### 11.5 Партии закупок (журнал, с 2026-05-18)

Всё редактирование количества/закупки товара — внутри модалки
«Редактировать товар» (раздел «Партии закупок» + «Поправить остаток»).
Старого поля-угадайки «количество» нет.

**Модель — журнал, НЕ FIFO.** Партия (`product_batches`) = запись о
закупке: номер, дата, закупочная цена, размеры/количества (jsonb
`[{size_id,size,quantity}]`). Остатки по размерам со всех партий —
**единый пул** (`product_sizes.current_quantity`, как и раньше); по
партиям сток НЕ разносится, при продаже не «списывается из конкретной
партии». Партии — источник правды только для:

- **«всего закуплено»** по размеру = Σ количеств по всем партиям
  (→ `product_sizes.initial_quantity`, `products.purchase_quantity`);
- **закупочной цены товара** = **средневзвешенная**
  = `Σ(цена_партии × штук_в_партии) / Σ(штук_в_партии)`
  (→ `products.purchase_price`). По ней как и раньше считаются прибыль
  §9.4 и ₽-недостача §11.4 — ядро денег не менялось, изменился лишь
  источник `purchase_price` (теперь дериват из партий, не ручной ввод).

Всё пересчитывается атомарно (RPC, метод проекта) при любом изменении
партий: `add_product_batch` / `edit_product_batch` /
`delete_product_batch` / `create_first_batch` →
`_recompute_product_from_batches`.

- **Добавить партию:** `current += qty` по размерам **и** партия в
  журнал. Это единственное «потрачены деньги», на недостачу не влияет.
- **Править/удалить партию:** остаток сдвигается на дельту размеров,
  **с защитой от минуса** (`GREATEST(0, …)`); «всего закуплено» и
  средняя цена пересчитываются. Удалить **единственную** партию нельзя.
- **Создание товара / существующие товары:** заводится «Партия 1»
  (`create_first_batch`; backfill миграцией `20260518000040`).

**«Поправить остаток» (§11.4) — отдельная ось** (физфакт vs система),
живёт там же в модалке, партии не трогает. Закупочная в форме товара —
read-only («средняя по партиям»).

### 11.6 Размеры и замеры по категории (с 2026-05-18)

Набор размеров и поля замеров **подстраиваются под категорию товара**
(единый конфиг `lib/constants/product-form-config.ts`; используется
формой создания И редактирования). Раньше размеры были захардкоженным
буквенным списком, замеры ввести было негде.

- **Режимы размеров** (`sizeMode` по категории):
  - Верхняя одежда, Костюмы → **letters** (буквы XXS…XXXL тогглами).
  - Нижняя одежда → **jeans**: буква + **опциональная** цифра →
    идентификатор размера `«M»` или `«M (31)»` (одна строка, ключ
    везде — сток/резерв/партии/недостача). Сортировка понимает формат
    (по букве, цифра — вторичный ключ).
  - Обувь → **shoe**: свободный ввод чисел (36, 41, 41.5 — любой).
  - Аксессуары → **oneSize**: единственный «One Size».
- **Замеры пер-размер** (см, опционально), поля по категории:
  - Верхняя: длина рукава, длина (плечо→низ), ширина туловища.

  - Костюмы: все 6 (верх + низ).
  - Обувь: длина стопы.
  - Аксессуары: замеров нет.
- **Хранение.** `product_sizes.measurements` jsonb (label→см, пер-размер).
  Создание — атомарно в `create_product_with_sizes` (замеры внутри
  элементов `p_sizes`). Редактирование — `set_product_size_measurements`

## 15. Авито-заказы с личных магазинов владельца

> Источник: ТЗ Авито-заказы (2026-05-30), миграции `20260530000001..05`.
> Архитектура зафиксирована: единая таблица `orders` с `source='avito'`,
> Avito-заказ живёт рядом с дроп-заказом, отправщик и финансы работают
> с обоими каналами в общем пуле.

### 15.1 Архитектура

- **Единая таблица `orders`** с дискриминатором `source IN ('drop','avito')`.
  Avito-специфичные поля: `avito_order_id`, `avito_buyer_name`,
  `avito_delivery_address`, `avito_fee_snapshot`, `avito_marketing_snapshot`,
  `delivered_at`, `return_initiated_at`, `return_arrived_at`.
- **`customer_id = NULL`, `partner_id = NULL`** для всех Avito-заказов.
  Покупатель Avito не в нашей системе — общение только через Avito-чат.
- **`avito_orders`** — raw-кеш API-ответа, используется существующими UI
  Avito-панели (объявления, операции). Канонический заказ живёт в `orders`.
- **Listing↔Product mapping**: `avito_item_product_mapping` (avito_item_id
  → product_id), заполняется владельцем вручную через
  `/owner/avito/items`. Модель — **одно объявление = один товар, размер
  уточняется через чат** (`product_size_id` появляется после ответа
  покупателя).

### 15.2 Статусы (расширение §4.2)

Три Avito-only статуса (только при `source='avito'`):

| Статус              | Что значит                                                              |
| ------------------- | ----------------------------------------------------------------------- |
| `awaiting_size`     | Заказ создан, размер неизвестен. Мини-AI пишет покупателю в Avito-чат.  |
| `delivered`         | Покупатель забрал из ПВЗ Авито (терминальный успех).                    |
| `return_in_transit` | Возврат покупателя в пути на ПВЗ (с `expected_return_date` из API).     |

State machine дроп-заказа (§4.4) их **не использует**.

### 15.3 Маппинг Avito-статусов → наши

Реализован в `src/lib/avito/order-sync.ts:mapAvitoStatusToOrderStatus`:

| Avito raw                        | Наш статус            |
| -------------------------------- | --------------------- |
| `voided` / `cancelled`           | `cancelled`           |
| `accepted` / `delivered`         | `delivered`           |
| `return_completed`               | `return_done`         |
| `on_delivery_return`             | `return`              |
| `*return*` (прочие)              | `return_in_transit`   |
| `payment_complete` / `packing`   | `paid` (если размер уточнён) или `awaiting_size` |
| `in_delivery` / `in_transit`     | `sent`                |

Список будет расширен по мере появления новых статусов на боевых заказах.

### 15.4 Жизненный цикл (расширение §4.4)

```
awaiting_size → paid           — покупатель ответил размер, сток зарезервирован
awaiting_size → cancelled      — не ответил в таймаут (12ч по дефолту) / send_by сгорел
paid → collecting → sent       — как у дропа
sent → delivered               — покупатель забрал из ПВЗ Авито
sent | delivered → return_in_transit → return → return_done
```

Сток **НЕ резервируется** в `awaiting_size` (размер ещё неизвестен).
Это значит параллельный дроп-заказ может выкупить последнюю единицу —
это ожидаемо, обрабатывается через перезапрос «остались только L, XL».

### 15.5 Финансы (расширение §9.4)

```
Avito-заказ:
  ownerRevenue = client_price (gross, цена объявления)
  ownerCost    = purchase_price
               + shipper_rate_snapshot
               + COALESCE(avito_fee_snapshot, 0)
               + COALESCE(avito_marketing_snapshot, 0)
  ownerProfit  = ownerRevenue − ownerCost
```

Канон-формулы в `src/lib/finance/owner-revenue.ts` (`ownerCost` уже
учитывает оба snapshot'а через `??` оператор).

`isRevenueCounted` (см. §9.3) расширен:
- `delivered` ≈ `sent` (в выручке)
- `return_in_transit` ≈ `return` (в выручке, деньги ещё у владельца)
- `awaiting_size` — НЕ в выручке (заказ не подтверждён)

Если Avito-API не отдаёт маркетинг per-order (Open Q4 в ТЗ) — фоллбэк:
маркетинг учитываем в журнале расходов на уровне периода, а
`avito_marketing_snapshot` остаётся NULL.

### 15.6 Возвраты (расширение §11.1)

Подбор возврата для problem-заказа (`out_of_stock`):

- **Выборка для Авито-кандидатов**: status `IN ('return', 'return_in_transit')`.
  Возврат-в-пути — основной кандидат (известна `expected_return_date`).
- **Авито-возврат**: привязываем только если
  `expected_return_date <= send_by − 1 день`. В день дедлайна
  отправщик не успеет.
- **Дроп-возврат** остаётся как было (`status='return'` + сегодня).
- **Avito-возврат с `expected_return_date IS NULL`** — аномалия (Avito
  обязана отдать дату). Skip + алерт владельцу.

### 15.7 Что НЕ применяется к Avito

| Механика                    | Почему                                                  |
| --------------------------- | ------------------------------------------------------- |
| `customer_balance` пополнение | `customer_id IS NULL` — `credit_customer_for_order` скипается естественно. Возврат денег покупателю Avito делает сама. |
| Trumpet-сессия              | Покупатель не в нашем боте, DM смысла не имеет. Фильтр `customer_id` уже скипает. |
| +ВАЙБ-кредит                | Авито принимает оплату до отгрузки, `is_paid=true` всегда. |
| Vision auto-confirm чека    | Нет чеков от Авито (он сам обрабатывает оплату).        |
| Wizard оформления           | Заказ приходит из API, без участия людей.               |
| Адаптивные пороги fault (§6.6) | Для trash Avito — DM директору, разбирается через кабинет Авито. |

### 15.8 Мини-AI продажник (размер)

1. Триггерится при upsert заказа в `awaiting_size` (если mapping есть).
2. Достаёт доступные размеры товара (`current_quantity > 0`).
3. Шлёт шаблонное сообщение в Авито-чат:
   _«Здравствуйте! Спасибо за заказ. Подскажите, пожалуйста, какой
   размер Вам нужен? Доступны: M, L, XL»._
4. Логирует в `avito_messages` с `is_ai_generated=true`.
5. Парсер ответа (`src/lib/avito/size-parser.ts`) — regex/словарь синонимов
   (`М/эм/эмка/м-ка` → M, и т.д.) + числовые размеры (42, 44, 46).
