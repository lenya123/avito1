## 1. Контекст

Сейчас в системе **только дроп-заказы**: клиент-дропшиппер в Telegram
оформляет через customer-bot, отправщик собирает и сдаёт в ПВЗ.
Конечный покупатель сидит на Авито, но к нам в систему не попадает —
дропшиппер потом сам перепродаёт ему под своим именем.

**Параллельно у владельца — собственные Авито-магазины**, где он
продаёт напрямую конечному покупателю Авито. Эти заказы сейчас живут
только в кабинете Авито: складом, отправщиком, аналитикой не
управляются. Задача — затащить этот поток к нам.

**По итогу должно работать:**

- Авито-**объявления** (товары в магазинах владельца) подтягиваются из
  API в нашу БД и связываются с нашими `products` (каждое объявление
  знает, какой товар из каталога владельца оно продаёт).
- Авито-**заказы** подтягиваются из API в нашу общую таблицу заказов
  с `source='avito'` — живут рядом с дроп-заказами.
- Когда в заказе **неизвестен размер** (Авито отдаёт только id
  объявления, не размер) — мини-AI-продажник инициирует диалог с
  покупателем в Авито-чате, спрашивает размер, получает ответ и
  проставляет его в заказ. Только после этого заказ становится виден
  отправщику в общем пуле.
- Подтягивается **полная логистическая история заказа** — таймлайн
  смены статусов (оплачен → отгружен → у курьера → в ПВЗ → забран →
  возврат инициирован → возврат на ПВЗ → забран нами).
- Отправщик собирает Авито-заказы через Shipper PWA из того же общего
  пула (приоритет по `send_by`).
- Складской учёт единый — Авито-продажа списывает сток с того же
  `products`, что и дроп.
- Аналитика и финансы учитывают Авито-заказы вместе с дроп-заказами,
  но с возможностью фильтровать по каналу.

**Что НЕ делаем в этом ТЗ:**

- **Качественный AI-продажник** (полноценный диалог, обработка
  возражений, поднятие конверсии). Владелец сам доделает поверх
  минимального ядра, которое ты построишь.
- **Полная админка магазинов/объявлений** (создание/редактирование
  объявлений из нашей панели). Подтяжка (read-only sync) — в скоупе,
  CRUD — отдельный ТЗ.
- Отдельные ценники Авито (`products.avito_price`).
- Sync полного диалога продавец ↔ покупатель в нашу систему (только
  AI-сообщения по размеру в этом ТЗ).

## 2. Архитектурные решения (зафиксированы)

| Решение         | Что выбрано                                                                                                                                                                                                                                  |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Скоуп           | Подтяжка объявлений + заказов + мини-AI для размера + UI/статусы. Полноценный AI и CRUD-админка — отдельные ТЗ.                                                                                                                              |
| Объявления      | Подтягиваем read-only через периодический sync. Каждое объявление имеет mapping к `products.id` (один-ко-многим: одно объявление = один товар, несколько размеров). При новом объявлении владелец вручную привязывает его к товару каталога. |
| Статусы         | Общий enum статуса заказа расширяется тремя новыми: `awaiting_size` (ждём ответа покупателя про размер), `delivered` (покупатель забрал из ПВЗ Авито), `return_in_transit` (возврат в пути на ПВЗ). State machine дропа их не использует.    |
| AI-продажник    | Минимальная версия: спрашивает размер шаблонным сообщением, парсит ответ через regex по доступным размерам товара. Не отвечает / не распознал → эскалация директору. Качественную надстройку (диалог, конверсия) сделает сам владелец позже. |
| Авито-расходы   | Два per-order снапшота: `avito_fee_snapshot` (комиссия Авито с продажи) и `avito_marketing_snapshot` (маркетинг на привлечение). Если маркетинг per-order невозможен — фоллбэк в журнал расходов (§6.3).                                     |
| Аналитика-split | Toggle «Все / Дроп / Авито» на Аналитике и Финансах + всегда видная карточка «Каналы сбыта» со сравнением метрик.                                                                                                                            |
| Логистика       | Полный таймлайн в `status_history` (через смену `orders.status`) + поля-снапшоты ключевых моментов на самом заказе (`delivered_at`, `return_initiated_at`, `return_arrived_at`).                                                             |

**Принцип реализации:** не дублируй функции — ветви существующую
логику по `source` (или по другому существующему дискриминатору вроде
`customer_id IS NULL`). Дроп-flow трогаем минимально, только в местах,
где Авито объективно требует другой логики.

## 3. Объявления и связь «Авито-листинг → наш товар»

### 3.1 Зачем

Когда из Авито API приходит новый заказ, в нём указан только
**id объявления** (Авито-листинга), но не товар нашего каталога и не
размер. Нам нужно:

- знать, какой `product` из нашего каталога продаётся через это
  объявление (для резерва стока и финансов);
- знать, какие размеры доступны на товаре (чтобы спросить покупателя
  только из существующих).

### 3.2 Что делаем

1. **Sync объявлений** — периодический job (или ручной запуск
   владельцем), который тянет из Avito API список всех объявлений
   магазинов владельца и upsert'ит их в нашу таблицу (например,
   `avito_listings` — если такая уже есть, переиспользуй; если нет —
   создаёшь). Поля: `avito_item_id`, `title`, `price`, статус
   объявления, ссылка, фото, и т.п.
2. **Mapping `avito_listings.product_id`** — поле в этой таблице,
   nullable, ссылка на `products.id`. Заполняется владельцем вручную
   через UI ниже.
3. **UI привязки** на `/owner/avito-listings` (или внутри карточки
   товара — на твой вкус):
   - Список объявлений со статусом «не привязано к товару» (бейдж
     красным сверху списка).
   - На карточке объявления — кнопка «Привязать к товару» → модалка
     с поиском по `products`.
   - На карточке товара (`/owner/products/[id]`) — блок «Авито-
     объявления» со списком привязанных листингов (read-only,
     отвязать можно).
4. **Когда приходит новый заказ из API без привязки объявления к
   товару** — заказ создаётся в `awaiting_size` (тот же статус, без
   нового 4-го). `product_id=NULL`, `product_size_id=NULL`,
   `system_comment='Авито-объявление не привязано к товару'`.
   AI-продажник **не запускается** (не знаем какие размеры
   спрашивать). Владельцу/директору — DM «Новый Авито-заказ, но
   объявление не привязано к товару — открой /owner/avito-listings».
   После привязки владелец вручную дёргает «Запустить AI-уточнение
   размера» на карточке заказа (или это автоматически после
   сохранения mapping'а — на твой вкус).

### 3.3 Размер ≠ объявление (важно)

В этом ТЗ работаем по модели **«одно объявление = один товар,
несколько размеров внутри»**. То есть объявление линкуется к
`products.id`, размер уточняется через диалог с покупателем (§4).

Если по факту окажется, что владелец публикует **каждый размер
отдельным объявлением** (некоторые продавцы так делают) — можно
дополнительно поддержать связь `avito_listings.product_size_id`
(nullable). Если она заполнена — заказ сразу создаётся с известным
размером, AI-продажник не запускается. См. Open Question #1.

## 4. Мини-AI продажник: уточнение размера

### 4.1 Зачем

Авито в заказе не отдаёт размер — он обсуждается в чате между
продавцом и покупателем. Чтобы система знала, что собирать, нам
нужен мини-AI, который ведёт этот короткий диалог автоматически.

**Полноценный AI-продажник** (с обработкой возражений, торгом,
конверсионными сценариями) **не в этом ТЗ** — его доделает владелец
поверх твоего минимального ядра.

### 4.2 Поток

1. Из API пришёл новый Авито-заказ → создаётся в `orders` с
   `status='awaiting_size'`, `product_size_id=NULL`, `product_id`
   = из mapping'а объявления (см. §3). **Сток на этом этапе НЕ
   резервируется** — мы не знаем какой размер. Это значит:
   параллельный дроп-заказ может выкупить последнюю единицу
   нужного размера, пока покупатель Авито думает. Это **ожидаемое
   поведение**, обрабатываем через перезапрос (см. п. 6).
2. Job-handler (например `avito-request-size` — или интегрируй в
   существующий `generate-sales-draft`) шлёт сообщение в Авито-чат
   через API:

   > Здравствуйте! Спасибо за заказ. Подскажите, пожалуйста, какой
   > размер Вам нужен? Доступны: **M, L, XL**.

   Список размеров — только те, что есть на товаре с
   `current_quantity > 0`.

3. Покупатель отвечает в Авито-чате (входящее сообщение приходит
   через polling или webhook — у тебя должно быть уже).
4. AI-парсер пытается извлечь размер из ответа. **Минимальная
   логика — regex/сравнение** по доступным размерам:
   - «M» / «эм» / «эм-ка» / «м-ка» → размер M
   - «L» / «эл» / «большой» → L
   - и т.д. — простой словарь
   - если не распознал → эскалация (см. п. 7)
5. **Размер успешно распознан, есть в наличии:**
   - Атомарно: `orders.product_size_id = X`, резерв стока (decrement
     `current_quantity` или `reserved_quantity`), статус заказа →
     `paid`.
   - В Авито-чат: «Спасибо, размер M зафиксирован. Ваш заказ
     №X скоро будет отправлен.»
6. **Размер распознан, но размер уже распродан** (между моментом
   запроса и ответом):
   - Перезапрашиваем: «К сожалению, M уже разобрали. Остались: L,
     XL. Какой подойдёт?»
   - Если все размеры распроданы → эскалация (см. п. 7).
7. **Эскалация в случаях:**
   - Покупатель не ответил в течение `business_settings.avito_size_request_timeout`
     (дефолт — например 12 часов).
   - Ответ не распознан 2 раза подряд.
   - Все размеры распроданы.
     → DM директору (с fallback на владельца) с контекстом: номер
     заказа, текст последнего сообщения покупателя, ссылка на
     Авито-чат. Дальше человек разбирается вручную через Авито.

### 4.3 Архитектурное место

Сама фронт-логика AI-продажника живёт в существующих BullMQ-job'ах
для Авито (`generate-sales-draft`, `send-approved-draft` — посмотри,
что там уже есть). Возможно, минимальная версия — отдельный job
`avito-request-size` без LLM (только шаблон + regex). Это **проще**,
быстрее и предсказуемее, чем сразу впихивать LLM. LLM появится в
следующей итерации, которую делает владелец.

### 4.4 Чем «минимальная» отличается от полной

| Аспект       | Минимальная (это ТЗ)                         | Полная (следующий ТЗ владельца)                              |
| ------------ | -------------------------------------------- | ------------------------------------------------------------ |
| Цель диалога | Получить размер                              | Получить размер + продать (закрыть возражения, торг, дожимы) |
| Тип ответа   | Шаблонные тексты                             | LLM-генерация под контекст                                   |
| Парсинг      | Regex / словарь                              | LLM-извлечение                                               |
| Сценарии     | 1 базовый (размер) + 1 fallback (распродано) | Десятки (вопрос-фото, скидка, доставка-вопрос, и т.п.)       |
| Эскалация    | После 2 нераспознанных → директор            | После исчерпания всех сценариев                              |

## 5. Жизненный цикл Авито-заказа

### 5.1 Поток

```
[Авито API: покупатель оформил и оплатил заказ]
   ↓
awaiting_size ✨    — заказ создан, размер неизвестен.
                      AI-продажник пинает покупателя в Авито-чате.
                      Сток ещё не зарезервирован.
   ↓ (покупатель ответил, размер распознан)
paid                — размер проставлен, сток зарезервирован.
                      Заказ виден отправщикам в общем пуле.
   ↓
collecting          — отправщик взял в работу (та же логика, что у дропа)
   ↓
sent                — отправщик сдал в ПВЗ Авито-доставки
                      (для Авито это НЕ финал, а «мы своё сделали»)
   ↓
delivered ✨        — конечный покупатель забрал из ПВЗ.
                      Терминальный успех для Авито. Узнаём из API.

— Возвратная ветка (инициирует покупатель Авито) —

sent | delivered
   ↓
return_in_transit ✨— покупатель оформил возврат, посылка едет к нам.
                      Знаем `expected_return_date` из API.
   ↓
return              — возврат приехал на ПВЗ (то же значение, что у дропа).
                      Появляется в PWA отправщика в табе «Возвраты».
   ↓
return_done         — отправщик забрал, сток восстановлен.

— Тупиковые ветки —

awaiting_size → cancelled    — покупатель не ответил вовремя / распродано
                                / `send_by` сгорел (Авито диктует дедлайн,
                                а покупатель так и не определился).
                                Эскалация директору, заказ закрываем,
                                Авито дёргается через cancel-endpoint.
paid → cancelled             — `send_by` сгорел до сборки.
                                То же: cancel-endpoint Авито.
return → trash               — pickup_by истёк. Для Авито §6.6 (адаптивные
                                пороги) НЕ применяется — просто DM директору,
                                разбирается через Авито-кабинет.
```

| `customer_id`            | Запись в `customers`                        | NULL                                                                                |

| Терминальный успех       | `sent`                                      | `delivered`                                                                         |

## 6. Финансовая модель

### 6.1 Формула прибыли (расширение §9.4 канона)

```
Дроп-заказ:
  ownerRevenue = client_price
  ownerCost    = purchase_price + shipper_rate_snapshot
  ownerProfit  = ownerRevenue − ownerCost

Авито-заказ:
  ownerRevenue = client_price (gross, цена объявления)
  ownerCost    = purchase_price
               + shipper_rate_snapshot
               + avito_fee_snapshot        ← комиссия Авито с продажи
               + avito_marketing_snapshot  ← маркетинг на привлечение
  ownerProfit  = ownerRevenue − ownerCost
```

Оба новых поля — NUMERIC ₽, заполняются при синке заказа из API.

### 6.2 Где показываем расходы канала

На странице Финансов и в карточке «Каналы сбыта» — блок:

```
Расходы канала Авито за период:
  Комиссии с продаж:               12 450 ₽
  Маркетинг (продвижение):          4 800 ₽
  ──────────────────────────────  ─────────
  Итого:                           17 250 ₽
```

В карточке «Каналы сбыта» (§7.2) — сумма «Итого» как summary-цифра.
В журнале расходов на Финансах — разбивка.

### 6.3 Фоллбэк: если маркетинг не per-order

Если Авито-API не отдаёт маркетинговый расход, привязанный к
конкретной продаже (владелец оплачивает продвижение магазина целиком,
а не объявления) — храним маркетинг как **отдельную строку в
существующем журнале расходов** с категорией «Авито-маркетинг».
`avito_marketing_snapshot` на заказе не используется, формула прибыли

## 8. Логистическая история заказа

### 8.1 Что подтягиваем

По каждому заказу из Авито API сохраняем минимум:

- Когда покупатель оформил и оплатил.
- Когда мы спросили размер / получили ответ (если AI-flow).
- Когда мы (отправщик) сдали в ПВЗ Авито (наш `sent`).
- Когда курьер забрал из ПВЗ-отправителя.
- Когда посылка приехала на ПВЗ-получателя.
- Когда покупатель забрал (наш `delivered`).
- Возврат: инициирован → поехал → приехал → забран нами.

### 8.2 Как храним (два слоя)

1. **`status_history`** (существующая таблица всех смен `orders.status`)
   — bridge при `UPDATE orders SET status = ...` автоматически фиксирует
   переход с timestamp'ом существующим триггером. Основной источник
   истории.
2. **Поля-снапшоты ключевых моментов на самом `orders`** — для
   быстрого рендера и аналитики без join'а:
   - `shipped_at` (есть у дропа — переиспользуем).
   - `delivered_at` (новый).
   - `return_initiated_at` (новый).
   - `return_arrived_at` (новый).
   - `expected_return_date` (есть в БД — обновляется при синке).

### 8.3 Где показываем

- **`/owner/orders/[id]`** — раздел «Таймлайн логистики»: вертикальный
  стек точек со временем. Для Авито богаче, для дропа короче.
- **Shipper PWA, карточка заказа** — компактная горизонтальная полоса
  «оплачен → собран → отправлен → у покупателя» с подсветкой текущей.
- **DM владельцу/директору** — только на трёх значимых событиях:
  `delivered`, `return_initiated`, `return_arrived`. Не на каждом
  шажке доставки (это спам). Роутится через
  `business_settings.notifications`.

## 9. Дополнительные нормативы (не покрытые таблицей §5.2)

1. **Подбор возврата под problem-заказ (`out_of_stock`).** Сейчас в
   коде ищем возврат того же `product_size_id` в статусе `return` с
   `expected_return_date <= send_by`. Расширяем:
   - **Выборка**: для Авито-кандидатов включить ещё и
     `status='return_in_transit'` (возврат в пути с известной датой
     прибытия — основной кандидат). Для дропа — только `return` как
     и сейчас.
   - **Дроп-возврат** (`expected_return_date IS NULL`, клиент сам
     отметил «приехал на ПВЗ») → берём `today` как эффективную дату,
     привязываем если `today <= send_by`.
   - **Авито-возврат** (`expected_return_date` известна из API) →
     привязываем только если `expected_return_date <= send_by − 1 день`.
     В день дедлайна отправщик не успеет.
   - **Авито-возврат с `expected_return_date IS NULL`** — аномалия
     (Авито должна была отдать дату). Skip и алерт владельцу.

2. **Отмена заказа на нашей стороне.** Если мы внутренне отменяем
   заказ (problem без подходящего возврата, send_by сгорел,
   `awaiting_size` истёк) — Авито должна об этом узнать через API
   (cancel endpoint). Покупателю Авито деньги возвращает сама.
   См. Open Question #2.

3. **Что Авито вообще не использует** (важно НЕ путать): wizard
   оформления, +ВАЙБ, `customer_balance`, withdrawal, anti-replay,
   Vision, Trumpet, partner-flow, customer-bot/partner-bot. Авито-
   заказ — без `customer_id`, без `partner_id`. Большинство уже
   существующих условий, проверяющих `customer_id IS NOT NULL` или
   `partner_id IS NULL`, корректно скипают его сами — проверяй,
   не переусложняй через явный `source` где можно обойтись.

4. **Генерация Авито-стикера (наш `tracking_number`).** Для дропа
   клиент присылает трек, мы только сохраняем. Для Авито — мы сами
   запрашиваем стикер через Авито API. Момент генерации —
   **при переходе из `awaiting_size` в `paid`** (как только заказ
   готов к сборке: размер известен, сток зарезервирован). Stike
   получаем синхронно или job'ой — твой выбор; главное к моменту,
   когда отправщик берёт `collecting`, `tracking_number` уже есть
   в `orders` (label-generator.ts уже умеет различать source при
   генерации QR/стикера для печати).

5. **Логирование AI-сообщений.** Все сообщения, которые мини-AI шлёт
   в Авито-чат, и ответы покупателя — пишем в БД (отдельная таблица
   `avito_chat_messages` или существующая, если есть). Поля минимум:
   `order_id`, `direction` (`out`/`in`), `text`, `created_at`,
   `parsed_size` (если ответ распарсен). Нужно для аудита AI-flow,
   отладки парсера и будущей доработки качества (это владелец увидит
   когда сядет за полноценный AI).

### 11.2 End-to-end жизненного цикла заказа

Прогнать на тест-магазине Авито целиком:

4. Покупатель оформляет заказ на Авито → через N минут заказ в
   `/owner/orders` со `source='avito'`, статусом `awaiting_size`,
   бейджем «Авито», заполнены `avito_buyer_name`,
   `avito_delivery_address`, `tracking_number`, `client_price`,
   `send_by`, `avito_fee_snapshot`, `avito_marketing_snapshot`
   (или фоллбэк). `product_id` подставлен из mapping'а объявления.
5. В Авито-чате появилось сообщение от нас «какой размер нужен?»
   с актуальным списком наличия.
6. Покупатель пишет «эл-ка» / «L» → размер распознан, заказ →
   `paid`, сток зарезервирован, в чате благодарность.
7. В Shipper PWA отправщик берёт заказ → `collecting`. Сдаёт в ПВЗ
   → `sent`. `shipper_rate_snapshot` записан.
8. При синке (Авито подтвердил получение покупателем) → `delivered`.
   В таймлайне `/owner/orders/[id]` видны все точки с временем. DM
   владельцу/директору ушёл.
9. Возврат от покупателя → синк → `return_in_transit` с датой
   прибытия. На карточке заказа видно «возврат в пути, прибудет
   DD.MM».
10. Возврат приехал на ПВЗ → синк → `return`. Появляется в PWA
    отправщика в табе «Возвраты».
11. Отправщик забрал → `return_done`. Сток восстановлен.
    `customer_balance` НЕ менялся ни разу за весь цикл.

### 11.3 Edge cases AI-flow

12. Покупатель не ответил за таймаут → заказ остался
    `awaiting_size` → cancelled, DM директору.
13. Покупатель ответил мусором («да-да») 2 раза подряд → эскалация

14. Покупатель попросил размер, который как раз распродали → новый
